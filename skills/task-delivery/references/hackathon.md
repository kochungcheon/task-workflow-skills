# 3시간 해커톤과 시험 대비

MD로 주어진 요구를 구현하며 사용자가 생성 문서로 맥락을 확인하고, 기능마다 자기 말로 설명하는 모드다. 다른 제한 시간이 주어지면 그 시간을 쓴다. 일반 개발에서 자동으로 학습 절차를 추가하지 않는다.

## 시간과 작업 크기

- `plan.md`에 `workflow_mode: hackathon-exam`, 원본 MD 위치, 요구 ID별 작업 연결, 시작·마감 시각, 필수 제출 항목을 적는다. 실제 시작 시각이 없으면 미확인으로 두고 남은 시간을 추정 사실처럼 쓰지 않는다.
- 180분의 기본 배분은 요구 파악·핵심 결정·분해·첫 지도 15분, 기능별 구현·검증·자기 설명 145분, 전체 실행·제출 점검·복습 정리 20분이다. 환경 준비·문서 작성·화면 확인도 이 시간에 포함한다. 실측 전의 운영안이며 사용자 제약과 실제 진척에 맞춰 조정한다.
- 한 기능은 구현·검증·설명을 포함해 대략 15~25분에 끝낼 수 있는 관찰 가능한 경로로 자른다. 고정된 개수에 맞추거나 API·UI 같은 계층만으로 나누지 않는다.
- 기능 인계 때 남은 시간과 필수 요구의 진척을 짧게 갱신한다. 초과가 예상되면 선택 기능을 뒤로 보내는 안을 제시하고, 필수 요구의 변경은 사용자와 확인한다. 시간 부족을 테스트·공동 E2E 통과로 바꾸지 않는다.

## 병렬 준비와 한 기능 집중

초기 사실 조사는 원문 요구 추출, 기존 코드·데이터 경로 탐색, 실행·검증 환경 확인으로 나눌 수 있다. 서로의 파일·상태를 바꾸지 않는 독립적인 읽기 전용 작업이고 서브 에이전트를 쓸 수 있으면 동시에 조사한다. 결과를 하나의 `plan.md` 초안에 합치고 충돌·누락을 대조한 뒤 사용자와 기술 선택을 논의한다. 독립성이 불분명하거나 수행자가 없으면 순차 조사한다.

이후에는 현재 기능 하나가 사용자와 에이전트의 공통 초점이다. TDD 수행자가 코드를 구현하는 동안 사용자는 구현 전 합의한 현재 기능의 지도·결정을 읽는다. 현재 에이전트나 별도 수행자는 같은 기능의 E2E 입력·검증 환경을 읽기 전용으로 준비할 수 있다. 다음 기능의 상세 설계·코드 구현은 현재 기능의 공동 E2E와 사용자 설명 뒤에 시작한다. 병렬 가능성이 애매하면 해당 병렬 작업을 생략한다.

## 계속 읽을 문서

`plan.md`는 전체 구현 목표·핵심 결정과 이유·작업 순서·복습 색인, 현재 `tasks/<task_id>.md`는 기능 범위·동작·검증·이해 기록의 원본, `maps/view.html`은 사용자가 계속 읽는 화면이다. 첫 화면에 전체 흐름에서 현재 위치와 작업별 구현 기록으로 가는 길을 표시한다. 현재 작업의 예정 경로·선택 이유·실패 조건·검증 지점을 TDD 전에 채워 사용자가 구현 중 읽게 한다. 구조·결정·검증 경계가 바뀌면 구현을 잠시 멈추고 해당 기록을 갱신해 사용자에게 알린다. 인계 때 계획과 실제 코드·근거를 대조해 갱신하며, 후속 작업은 미구현 개요로 둔다. 기존 두 지도와 HTML의 변경 부분을 갱신한다.

문서 작성은 에이전트가 맡고, 사용자는 중요한 선택·결과·자기 설명에 참여한다. 초안을 보면서 대화하고 결정과 이유를 그때 반영한다. 확정 요구는 원문에서 가져오며, AI가 제안한 설계를 사용자 결정으로 기록하지 않는다. 전체 순서를 먼저 잡고 현재 기능부터 상세화한다. 결정이 바뀌면 `plan_revision`을 올리고 영향을 받는 작업·지도·검증 지점을 맞춘다. 범위·검증 경계·선택 이유가 달라진 작업의 `task_revision`도 갱신한다.

## 현재 작업의 TDD 위임

서브 에이전트를 사용할 수 있는 해커톤 모드에서는 현재 작업의 범위·검증 경계와 지도를 사용자와 확인한 뒤, TDD 구현만 전담 서브 에이전트 하나에 맡긴다. 현재 에이전트는 설계 대화, 계획·지도·상태, 사용자 소통, 코드 검토, 인계·공동 E2E를 맡는다. 사용자는 열린 `maps/view.html`과 작업 MD를 읽으며 구현 맥락을 따라간다. 한 작업의 공동 E2E와 설명을 마치기 전에는 다음 작업을 시작하지 않는다.

위임할 때 현재 과제 MD·원본 요구·계획·두 지도 경로와 `plan_revision / task_revision / map_revision / code_ref`, 합의한 결정·공개 테스트 경계, 허용된 코드 범위를 전달한다. 수행자에게는 실제 Red/Green 로그, 변경 파일, 회귀 결과, 막힌 선택을 보고하게 한다. 수행자는 계획·지도·작업 상태·공동 E2E 판정을 바꾸지 않는다. 현재 에이전트는 같은 코드 파일을 동시에 편집하지 않고, 막힌 결정이 오면 사용자와 정리해 패키지를 갱신한 뒤 구현을 재개한다.

서브 에이전트 결과를 받으면 현재 에이전트가 코드와 실행 근거를 대조하고, 필요한 회귀 검사·지도 갱신·`task-evidence` 인계를 완료한다. 서브 에이전트가 없거나 사용자가 직접 구현을 지정하면 현재 에이전트가 같은 TDD 절차를 수행한다.

구현량이 많은 3시간 과제에서는 별도 PRD·intent 문서나 단계별 평가표를 추가하지 않는다. 이미 있는 `plan.md`에 목표·성공 기준·기존 구조에서 이어받는 전제와 핵심 결정만 남기고, 현재 작업의 지도·근거부터 갱신한다. 초반의 사용자·AI 설계 대화는 실제 구현 방향을 바꾸는 쟁점에 충분히 쓰고, 그 결과를 같은 문서와 HTML에 압축한다. 뒤에서 반복되는 문서 재작성과 불필요한 승인 절차를 줄인다. 기능별 공동 E2E와 사용자 설명의 경계는 유지한다.

## 티켓 분해와 기술적 선택 대화

처음 티켓을 나눌 때 요구 전체와 기존 코드를 훑어 **방식이 달라지면 작업 경계·정합성·복구·검증 방법이 달라지는 지점**을 찾는다. 원문이나 코드에서 확인 가능한 사실은 근거를 찾아 적고, 사용자에게는 목표·범위·동작·절충처럼 실제 선택이 필요한 것만 묻는다. 후보마다 결정할 질문, 연결된 요구·작업, 현실적인 선택지와 득실, 추천안·적용 조건을 `plan.md` **초안으로 먼저** 적어 보여준다. 현재 구현에 영향을 주는 쟁점부터 사용자와 왕복한다: 에이전트가 실제 동작 예와 실패 조건을 설명하고, 사용자의 질문·반론·우선순위에 따라 대안을 다시 비교해 초안을 고친다. 설계가 바뀌면 관련 작업 경계와 검증 지점도 함께 수정한다. 아직 답이 없는 항목은 `제안/미확인`으로 표시해 관련 작업 전까지 남겨둔다. 이미 결정한 항목을 작업마다 다시 묻지 않고, 표현이나 상태 코드 같은 세부 선택을 모두 사전 합의 대상으로 만들지 않는다.

가정은 `plan.md`의 남은 가정 표에 근거·영향·확인 시점을 남기고, 적용된 작업 MD와 HTML에도 표시한다. 현재 작업의 구조·인수 기준을 바꾸는 미확인 선택은 진행 전에 해결한다. 후속 작업의 선택과 결과에 큰 영향이 없는 가정은 표시한 채 초안을 발전시킨다. 사용자가 “알아서 결정해줘”처럼 판단을 위임하면 합의로 둔갑시키지 말고 에이전트 선택·이유·영향을 기록해 진행한다. 정해진 질문 수를 채우려고 대화를 늘리지 않는다.

사용자가 선택한 내용과 에이전트가 스스로 택한 내용을 구분한다. 대화 전에 만들어 둔 지도는 제안 상태로 표시하고, 결정 후에는 `plan.md`의 결정 ID·이유·대안·적용 범위와 **대화로 달라진 설계**를 갱신한다. 객체 지도는 영향을 받는 책임·경계에 결정 ID를 연결하고, HTML은 현재 선택의 요약과 남은 쟁점을 읽기 쉽게 보여준다. 현재 작업의 설계·지도·검증 지점을 사용자가 검토할 수 있게 보여준 뒤 구현한다. 구현 중 다른 선택이 필요해지면 같은 결정 항목을 다시 열어 이유와 영향을 대화한 뒤 코드·지도에 반영한다.

구현 인계 시 현재 과제에 다음을 짧게 남긴다.

- 원본 요구 ID와 사용자에게 보이는 변화.
- 입력 → 주요 노드/함수 → 외부 경계/저장 → 결과.
- 실제 구현에서 택한 방법과 이유, 고려한 대안·트레이드오프가 있다면 한 가지. 원래 논의하지 않은 대안을 실제 결정 이력으로 만들지 않는다.
- 영향을 받는 결정 ID와 실제 코드·검증에서 확인된 점. 선택 이유와 구현 결과가 달라지면 결정 기록을 정정한다.
- 실패 입력·조건과 처리 경로.
- 테스트로 확인한 범위와 아직 확인하지 못한 범위의 근거 링크.

## 기능 검증 뒤 60~90초 자기 설명

1. 현재 코드의 필수 공동 E2E와 사용자 결과 확인을 마친 뒤, 한 번에 짧게 묻는다. **“이 기능은 입력부터 결과까지 어떻게 흐르고, 핵심 구현을 왜 이렇게 선택했나요? 막힌 부분도 같이 말해주세요.”** 가능하면 문서를 잠깐 덮고 자기 말로 설명하도록 권한다. 응답을 받기 전 다음 기능 구현을 시작하지 않는다.
2. `task-evidence`의 `learning-review`에 현재 과제·지도·코드와 실제 사용자 응답을 전달한다. 동작 흐름과 선택 이유를 각각 확인한다. 문장 표현이나 용어 암기보다 실제 인과관계를 본다.
3. 막힘·오해가 있으면 해당 노드/코드를 가리켜 짧게 보충한다. 필요하면 가장 중요한 한 지점만 한 번 다시 물어본다. 추가 응답을 받기 전에는 최초 막힘이 해소되었다고 기록하지 않는다. 긴 문답이나 고정 문항 시험으로 확장하지 않는다.
4. 응답과 남은 복습 지점을 과제 파일에 기록한다. `explained` 또는 `revisit`이면 다음 기능으로 진행할 수 있다. 이해가 덜 된 항목은 복습 대상으로 남기며 기능의 `verified` 판정과 분리한다. 설명 과정에서 실제 코드 오류가 확인되면 기존 회귀 처리에 따라 같은 기능을 다시 연다.
5. 사용자가 설명을 명시적으로 보류하면 `deferred`와 그 발언을 기록하고 진행한다. 응답이 없으면 `pending`으로 기다린다. 시간 경과나 단순한 “계속”은 설명 완료·보류 근거가 아니다. 이미 같은 기능·버전에 대해 흐름과 이유를 설명했다면 그 응답을 재사용한다.

60~90초는 짧은 설명을 위한 목표이며 자동 타임아웃이 아니다. 문서의 다섯 항목은 짧게 유지하고 말로 확인할 때는 동작 흐름·선택 이유를 중심으로 한다. 별도 요청한 전체 작업 후 6문항 연습은 이 기능별 확인과 구분한다. 실제 시험 문제나 점수를 예측하지 않는다.

## 종료와 재개

마지막 20분에는 전체 필수 경로와 제출물을 점검하고, `plan.md`에 `revisit`·`deferred`·`pending` 항목을 과제의 이해 기록으로 연결한다. 시간이 남으면 중요한 막힘부터 짧게 다시 설명받는다. 해결 여부는 새 응답과 현재 코드로 확인하고 이전 기록을 보존한다.

재개 시 `plan.md`의 모드와 과제의 `state`·`learning_status`를 읽는다. 코드·선택 이유가 바뀌면 영향을 받은 설명을 다시 확인하고 이전 설명의 코드 식별값을 보존한다. 구현 완료를 이해 완료로 합치지 않는다.
