# 3시간 해커톤과 시험 대비

MD로 주어진 요구를 구현하며 사용자가 생성 문서로 맥락을 확인하고, 기능마다 자기 말로 설명하는 모드다. 다른 제한 시간이 주어지면 그 시간을 쓴다. 일반 개발에서 자동으로 학습 절차를 추가하지 않는다.

## 시간과 작업 크기

- `plan.md`에 `workflow_mode: hackathon-exam`, 원본 MD 위치, 요구 ID별 작업 연결, 시작·마감 시각, 필수 제출 항목을 적는다. 실제 시작 시각이 없으면 미확인으로 두고 남은 시간을 추정 사실처럼 쓰지 않는다.
- 180분의 기본 배분은 요구 파악·핵심 결정·분해·첫 지도 15분, 기능별 구현·검증·자기 설명 145분, 전체 실행·제출 점검·복습 정리 20분이다. 환경 준비·문서 작성·화면 확인도 이 시간에 포함한다. 실측 전의 운영안이며 사용자 제약과 실제 진척에 맞춰 조정한다.
- 한 기능은 구현·검증·설명을 포함해 대략 15~25분에 끝낼 수 있는 관찰 가능한 경로로 자른다. 고정된 개수에 맞추거나 API·UI 같은 계층만으로 나누지 않는다.
- 기능 인계 때 남은 시간과 필수 요구의 진척을 짧게 갱신한다. 초과가 예상되면 선택 기능을 뒤로 보내는 안을 제시하고, 필수 요구의 변경은 사용자와 확인한다. 시간 부족을 테스트·공동 E2E 통과로 바꾸지 않는다.

## 계속 읽을 문서

`plan.md`는 전체 구현 목표·핵심 결정과 이유·작업 순서·복습 색인, 현재 `tasks/<task_id>.md`는 기능 범위·동작·검증·이해 기록의 원본, `maps/view.html`은 사용자가 계속 읽는 화면이다. 첫 화면에 전체 흐름에서 현재 위치를 표시하고, 현재 기능의 다섯 항목과 복습 지점을 연결한다. 기존 두 지도와 HTML의 변경 부분을 갱신한다.

문서 작성은 에이전트가 맡고, 사용자는 중요한 선택·결과·자기 설명에 참여한다. 초안을 보면서 대화하고 결정과 이유를 그때 반영한다. 확정 요구는 원문에서 가져오며, AI가 제안한 설계를 사용자 결정으로 기록하지 않는다. 전체 순서를 먼저 잡고 현재 기능부터 상세화한다. 결정이 바뀌면 `plan_revision`을 올리고 영향을 받는 작업·지도·검증 지점을 맞춘다. 범위·검증 경계·선택 이유가 달라진 작업의 `task_revision`도 갱신한다.

구현 인계 시 현재 과제에 다음을 짧게 남긴다.

- 원본 요구 ID와 사용자에게 보이는 변화.
- 입력 → 주요 노드/함수 → 외부 경계/저장 → 결과.
- 실제 구현에서 택한 방법과 이유, 고려한 대안·트레이드오프가 있다면 한 가지. 원래 논의하지 않은 대안을 실제 결정 이력으로 만들지 않는다.
- 실패 입력·조건과 처리 경로.
- 테스트로 확인한 범위와 아직 확인하지 못한 범위의 근거 링크.

## 기능 검증 뒤 60~90초 자기 설명

1. 현재 코드의 필수 공동 E2E와 사용자 결과 확인을 마친 뒤, 한 번에 짧게 묻는다. **“이 기능은 입력부터 결과까지 어떻게 흐르고, 핵심 구현을 왜 이렇게 선택했나요? 막힌 부분도 같이 말해주세요.”** 가능하면 문서를 잠깐 덮고 자기 말로 설명하도록 권한다. 응답을 받기 전 다음 기능 구현을 시작하지 않는다.
2. `task-evidence`의 `learning-review`에 현재 과제·지도·코드와 실제 사용자 응답을 전달한다. 동작 흐름과 선택 이유를 각각 확인한다. 문장 표현이나 용어 암기보다 실제 인과관계를 본다.
3. 막힘·오해가 있으면 해당 노드/코드를 가리켜 짧게 보충한다. 필요하면 가장 중요한 한 지점만 한 번 다시 물어본다. 추가 응답을 받기 전에는 최초 막힘이 해소되었다고 기록하지 않는다. 긴 문답이나 고정 문항 시험으로 확장하지 않는다.
4. 응답과 남은 복습 지점을 과제 파일에 기록한다. `explained` 또는 `revisit`이면 다음 기능으로 진행할 수 있다. 이해가 덜 된 항목은 복습 대상으로 남기며 기능의 `verified` 판정과 분리한다. 설명 과정에서 실제 코드 오류가 확인되면 기존 회귀 처리에 따라 같은 기능을 다시 연다.
5. 사용자가 설명을 명시적으로 보류하면 `deferred`와 그 발언을 기록하고 진행한다. 응답이 없으면 `pending`으로 기다린다. 시간 경과나 단순한 “계속”은 설명 완료·보류 근거가 아니다. 이미 같은 기능·버전에 대해 흐름과 이유를 설명했다면 그 응답을 재사용한다.

60~90초는 짧은 설명을 위한 목표이며 자동 타임아웃이 아니다. 문서의 다섯 항목은 짧게 유지하고 말로 확인할 때는 동작 흐름·선택 이유를 중심으로 한다. 별도 요청한 전체 작업 후 6문항 연습은 이 기능별 확인과 구분한다. 실제 시험 문제나 점수를 예측하지 않는다.

## 종료와 재개

마지막 20분에는 전체 필수 경로와 제출물을 점검하고, `plan.md`에 `revisit`·`deferred`·`pending` 항목을 과제의 이해 기록으로 연결한다. 시간이 남으면 중요한 막힘부터 짧게 다시 설명받는다. 해결 여부는 새 응답과 현재 코드로 확인하고 이전 기록을 보존한다.

재개 시 `plan.md`의 모드와 과제의 `state`·`learning_status`를 읽는다. 코드·선택 이유가 바뀌면 영향을 받은 설명을 다시 확인하고 이전 설명의 코드 식별값을 보존한다. 구현 완료를 이해 완료로 합치지 않는다.
