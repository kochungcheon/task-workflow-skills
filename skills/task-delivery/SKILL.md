# 한 서브 과제씩 검증하며 진행하기

사용자와 에이전트가 같은 과제·객체 지도·흐름 지도를 읽는다. 이 스킬은 도구를 조합하고 작업 상태를 관리한다. 실제 함수 호출이나 백그라운드 실행 엔진이 아니라, 코딩 에이전트가 따라 실행하는 절차다.

시작할 때 [공유 계약](../contracts/task-workflow-v1.md)을 읽고, 사용할 기능에 해당하는 [구성 요소](../contracts/components.md)를 확인한다. 분석·지도 작성만 요청했다면 그 범위까지만 수행한다. 실제 시험에서는 확인된 허용 도구·행동 범위가 우선이다.

해커톤·시험 대비로 진행할 때는 [시간 배분과 자기 설명 절차](references/hackathon.md)를 읽는다. 이 모드에서는 기능 검증 뒤 사용자 설명을 받고 이해가 막힌 부분을 기록한 다음 다음 기능으로 넘어간다.

## 시작 또는 재개

1. 과제 원문·제출 요구·기존 코드와 작업 기록을 읽는다. 기존 `.workflow/<과제명>/`이 있으면 실제 코드와 대조해 이어받는다. 새 기록은 아래 구조를 사용하되 같은 역할의 기존 파일이 있으면 재사용한다.

   ```text
   .workflow/<과제명>/
     plan.md                 전체 구현 방향·결정 이유·작업 순서·복습 색인
     tasks/T01.md             현재 상태의 원본, 한 파일에 한 과제
     maps/index.md            두 지도 버전·코드 근거·노드 색인
     maps/objects.mmd         객체·책임·인터페이스
     maps/flow.mmd            입력부터 결과까지의 실행 경로
     maps/view.html           사용자가 읽는 지도
     evidence/T01/            시도별 handoff·joint-e2e·실행 근거
   ```

2. [전체 구현 양식](assets/plan.md)을 참고해 `plan.md` 초안을 만든다. 과제·코드에서 확인할 사실은 직접 조사하고, 중요한 선택에는 선택지·추천·이유를 제시해 대화로 정리한다. 원문 요구, 사용자와 합의한 결정, AI 제안, 남은 가정을 구분한다. `to-tickets`의 분해 기준으로 입력부터 결과까지 확인 가능한 작은 기능의 순서·의존관계·인수 기준을 잡는다. 원문은 구성 요소 문서의 로컬 어댑터로 참고한다. 전체 순서를 보여주고 현재 과제부터 상세화하며 후속 과제는 `plan.md`의 개요로 둔다. 이미 합의한 결정과 분해는 재사용한다.
3. [과제 양식](assets/task.md)으로 현재 과제 하나를 구체화하고 전체 계획의 요구 ID·결정 ID를 참조한다. `task-maps`로 객체·흐름 지도를 만들고 인수 기준을 관찰할 공개 인터페이스를 표시한다. 사용자가 검토할 패키지는 과제·두 지도·TDD 검증 지점·E2E 경로다. **해당 과제의 범위와 검증 지점이 합의되고 선행 작업이 검증 완료일 때** `ready`로 둔다. 현재 구현을 바꾸는 미결정 사항은 먼저 해결하고, 일반적인 진행 동의를 새로운 검증 지점의 승인으로 해석하지 않는다.

## 한 번에 현재 과제 하나

4. `ready` 과제를 `implementing`으로 바꾸고 같은 과제 버전·지도 버전을 작업 에이전트에 전달한다. 기본 수행자는 현재 에이전트다. 별도 위임은 사용자가 요청한 경우에 하며, 그때도 현재 과제와 같은 패키지만 전달한다.
5. `tdd`를 읽고 합의한 공개 인터페이스에서 **테스트 작성 → 실제 실패 확인 → 최소 구현 → 실제 통과 확인**을 하나씩 반복한다. 기대값은 요구·업무 규칙에서 도출한다. 실행 환경 오류는 기능의 Red와 구분한다. 범위·인터페이스 변경이 필요하면 코드 확장 전에 과제·지도·합의를 갱신한다.
6. 구현 뒤 영향을 받는 회귀 검사를 실행하고 `task-maps`로 실제 코드와 지도를 맞춘다. `task-evidence`의 `handoff` 모드에 현재 과제·지도·코드 식별값과 실행 근거를 전달한다. 누락·실패·버전 불일치는 해당 과제에서 해결한다.
7. handoff 결과가 준비되면 `awaiting_joint_e2e`로 기록하고 사용자에게 다음을 보고한 뒤 이번 구현 실행을 끝낸다.
   - 구현한 동작과 선택 이유
   - 실제 Red/Green·관련 회귀 근거
   - 두 지도의 변경점과 현재 위치
   - 함께 실행할 E2E 입력·행동·기대 결과 및 미검증 범위

   이 상태의 표시명은 **구현 완료·공동 검증 대기**다. 모든 인수 기준의 검증 완료나 다음 과제 착수로 해석하지 않는다.

## 공동 E2E와 다음 과제

8. 사용자와 현재 산출물의 실제 경로를 확인한다. 허용된 환경의 UI·API·CLI 중 실제 진입점으로 입력하고 필요한 저장·조회·출력까지 관찰한다. `task-evidence`의 `joint-e2e` 모드로 실행 근거와 사용자의 결과 확인을 정리한다.
9. [상태 전이](../contracts/task-workflow-v1.md#상태-전이)에 따라 현재 과제를 처리한다. 실패는 같은 과제의 `fixing`, 환경·근거 부족은 `blocked`로 두고 원인을 해결한다. `awaiting_joint_e2e`에서 기다리는 것은 정상 협업 상태다.
10. 현재 버전의 필수 E2E가 통과하고 사용자가 결과를 확인한 경우만 `verified`로 바꾼다. 해커톤·시험 대비 모드에서는 여기서 짧은 자기 설명을 요청하고 사용자 응답을 기다린다. `task-evidence`의 `learning-review`로 현재 과제에 설명·막힌 부분·복습 지점을 남긴다. 다음 기능으로 넘어가는 조건과 명시적 보류는 [자기 설명 절차](references/hackathon.md)를 따른다.
11. `task-maps`로 전체 지도에 기능 검증 결과와 변경된 복습 표시를 반영하고 의존관계가 풀린 다음 과제 하나의 패키지를 보여준다. 이미 합의된 범위·검증 지점은 재사용하고 새 결정이 있는 부분만 확인한다. 마지막 과제까지 검증되면 제출 요구별 근거와 실행 방법을 인계한다. 해커톤·시험 대비에서는 남은 복습 지점도 함께 연결한다.

재개 시 이전 테스트 뒤 코드·기준이 달라졌는지 확인한다. 달라진 부분의 통과 근거를 다시 확보한다. 사용자의 단순한 “계속”만으로 공동 E2E 통과를 기록하지 않는다. 커밋·외부 이슈 게시·실제 제출은 이 스킬의 자동 부수 작업이 아니다.
