# 한 서브 과제씩 검증하며 진행하기

사용자와 에이전트가 같은 과제·객체 지도·흐름 지도를 읽는다. 이 스킬은 도구를 조합하고 작업 상태를 관리한다. 실제 함수 호출이나 백그라운드 실행 엔진이 아니라, 코딩 에이전트가 따라 실행하는 절차다.

시작할 때 [공유 계약](../contracts/task-workflow-v1.md)을 읽고, 사용할 기능에 해당하는 [구성 요소](../contracts/components.md)를 확인한다. 분석·지도 작성만 요청했다면 그 범위까지만 수행한다. 실제 시험에서는 확인된 허용 도구·행동 범위가 우선이다.

해커톤·시험 대비로 진행할 때는 [시간 배분과 자기 설명 절차](references/hackathon.md)를 읽는다. 이 모드에서는 기능 검증 뒤 사용자 설명을 받고 이해가 막힌 부분을 기록한 다음 다음 기능으로 넘어간다.

## 시작 또는 재개

1. 과제 원문·제출 요구·기존 코드와 작업 기록을 읽는다. 기존 `.workflow/<과제명>/`이 있으면 실제 코드와 대조해 이어받는다. 새 기록은 아래 구조를 사용하되 같은 역할의 기존 파일이 있으면 재사용한다.

   ```text
   .workflow/<과제명>/
     plan.md                 요구·고객 질문과 답변·설계 결정·작업 순서·복습 색인
     review.md               지금까지의 작업·결정·검증·설명 누적 복습
     tasks/T01.md             현재 상태의 원본, 한 파일에 한 과제
     maps/index.md            두 지도 버전·코드 근거·노드 색인
     maps/objects.mmd         객체·책임·인터페이스
     maps/flow.mmd            입력부터 결과까지의 실행 경로
     maps/view.html           사용자가 읽는 지도
     evidence/T01/            시도별 설계/코드 리뷰·handoff·joint-e2e·실행 근거
   ```

2. [전체 구현 양식](assets/plan.md)을 참고해 `plan.md` 초안을 먼저 만든다. 원문·기존 코드에서 확인할 수 있는 사실과 요구 ID를 정리한다. [개념·규칙·출처 기본 점검](../contracts/task-workflow-v1.md#개념과-규칙의-출처-연결)으로 동작을 바꾸는 용어의 의미·역할·관계와 규칙의 조건·예외를 원문·코드에 대조한다. 필요한 보완은 기존 요구·질문·인수 기준에 연결하고 정의의 정본을 참조한다. 권한·업무 규칙·데이터 소유권·상태 전이·실패와 복구·성공 기준에서 빈틈이나 충돌을 찾으면 [task-customer-interview](../task-customer-interview/SKILL.md)를 호출한다. 고객 확인이 필요한 정책과 기술 선택을 나누고, [고객 확인 결과 적용과 재개](#고객-확인-결과-적용과-재개)에 따라 현재 기능과 공통 구조를 바꾸는 답변을 반영한다. `to-tickets`의 분해 기준으로 입력부터 결과까지 확인 가능한 작은 기능의 순서·의존관계·인수 기준을 잡는다. 해커톤 모드의 독립 조사 병렬화와 결과 합치기는 [해커톤 절차](references/hackathon.md#병렬-준비와-한-기능-집중)를 따른다. **분해와 함께** 구조·상태·동시성·실패 처리 등 작업 경계나 정합성에 영향을 주는 기술적 갈림길을 찾는다. 뒤 작업의 요구가 현재 작업의 저장 구조·처리 순서를 바꾸는지도 확인한다. 중요한 것에는 결정 ID, 관련 요구·작업, 선택지의 득실, 추천과 이유, 아직 확인할 점을 적어 전체 순서와 함께 사용자에게 보여준다. `task-design-dialogue`로 사용자와 질문·반론·수정안을 왕복하며 현재 구현에 필요한 결정을 정한다. 원문 요구, 사용자와 합의한 결정, AI 제안, 남은 가정을 구분한다. 현재 과제부터 상세화하고 후속 과제는 개요로 둔다. 이미 합의한 결정과 분해는 재사용한다. 해커톤 모드에서는 `task-review`로 `review.md`에 현재 목표·작업 순서·열린 선택을 요약해 사용자가 읽을 문서를 시작한다. 공유 문서의 설명 문장은 [simple-english 문서 어댑터](../contracts/components.md#simple-english-문서-어댑터)로 점검한다. 해커톤에서 논의할 선택의 우선순위는 [해커톤 절차](references/hackathon.md)를 따른다.
3. [과제 양식](assets/task.md)으로 현재 과제 하나를 구체화하고 전체 계획의 요구 ID·고객 질문 ID·결정 ID를 참조한다. 새 작업과 재개하는 현재 작업에 `quality_policy: review-v1`을 기록하고 [QualityReview](../contracts/task-workflow-v1.md#qualityreview--설계코드-검토의-선택-확장)의 적용 범위와 프로젝트의 필수 구현 검사를 정한다. `ready` 판정 전에 정상·실패 상황의 기대값과 그 결과를 바꾸는 용어·규칙의 의미를 출처와 함께 정할 수 있는지 점검한다. 현재 작업에 필요한 미확인 정책이나 확인 시점이 된 질문은 `task-customer-interview`로 확인하고 인수 기준에 반영한다. 기존 답변은 적용 범위를 대조해 재사용한다. `task-maps`로 객체·흐름 지도를 만들고 인수 기준을 관찰할 공개 인터페이스와 결정이 영향을 주는 책임·경계를 표시한다. HTML에는 작업별 기록을 두고 현재 작업의 예정 구현 경로·선택 이유·검증 지점을 **TDD 시작 전에** 읽을 수 있게 한다. 후속 작업은 개요와 계획 상태로 둔다. 사용자가 검토할 패키지는 과제·두 지도·결정 요약·TDD 검증 지점·E2E 경로다. 아래 [품질 검토와 수정](#품질-검토와-수정)에 따라 중요한 설계를 독립 검토하고 결과를 같은 작업에 연결한다. **해당 과제의 범위·검증 지점 합의, 적용되는 설계 리뷰 충족, 선행 작업 검증 완료**를 확인한 뒤 `ready`로 둔다. 현재 구현을 바꾸는 중요한 미결정 사항은 선택지와 영향을 보여준 뒤 먼저 해결한다. 나중 작업에만 필요한 선택은 제안 상태로 두고, 사소한 내부 선택은 근거를 적은 가정이나 에이전트 판단으로 진행할 수 있다. 사용자가 판단을 맡기면 에이전트 선택으로 기록한다. 일반적인 진행 동의를 아직 제시하지 않은 선택의 합의로 기록하지 않는다.

## 고객 확인 결과 적용과 재개

- 인터뷰의 질문·답변·출처·변경 요약을 `plan.md`에 연결한다. 확정된 답변부터 관련 요구·작업·인수 기준에 반영하고 기술적 선택이 생기면 `task-design-dialogue`로 논의한다. 현재 작업의 필수 기대값을 결정하는 미해결 질문은 `ready` 판정 전에 확인한다. 인터뷰 결과의 `ready`와 작업의 `ready`는 각자의 조건으로 판단한다.
- `awaiting_answers`·`needs_clarification`은 질문별 대기로 기록한다. 현재 작업의 구조·필수 기준을 실제로 막으면 그 작업에 질문 ID·영향과 `blocked / resume_state`를 남긴다. 작업 분해 전이라면 계획의 질문과 영향을 기록한다. 후속 작업의 질문에는 확인 시점을 붙이고, 답과 무관한 조사·환경 준비는 진행한다. 고객에게 전달할 질문을 보여준 뒤 실제 답변을 기다린다.
- 새 답변·정정이 오면 [CustomerInterviewNote의 변경 규칙](../contracts/task-workflow-v1.md#customerinterviewnote--고객-정책-확인의-선택-확장)에 따라 계획·작업·지도·검증 기준을 갱신한다. 바뀐 경계의 합의를 확인한 뒤 원래 단계로 재개하며, 영향받는 검사와 기존 완료 작업의 재검증을 연결한다. 이전 답변과 검증 근거는 해당 버전의 이력으로 보존한다.

## 품질 검토와 수정

- `ready` 전에 [task-quality-review](../task-quality-review/SKILL.md)의 `design` 모드로 현재 구현을 바꾸는 중요한 설계를 검토한다. 원문 요구·실제 고객 답변·계획·작업 MD·지도·관련 코드를 명시적으로 전달하고 이전 대화를 제외한 새 리뷰어를 사용한다. 단순하고 명확한 작업에는 적용 제외 이유를 기록한다. 현재 버전의 유효한 검토는 재사용할 수 있다.
- 지적은 근거와 발생 조건을 대조한다. 고객 정책 공백은 `task-customer-interview`, 중요한 기술 선택은 `task-design-dialogue`, 구현 결함은 현재 과제의 `fixing`으로 연결한다. 변경된 기준·지도·코드의 식별값을 맞추고 영향받는 리뷰와 검사를 다시 확인한다. 범위나 합의된 선택이 바뀌면 기존 합의 규칙에 따라 사용자와 정리한다.
- 기본 한 차례 검토 후 주요 수정 범위를 재검토한다. 필수 검토의 미실행·근거 부족은 실제 차단 원인과 `resume_state`, 미해결 주요 지적은 수정할 항목으로 기록한다. 독립적으로 진행할 준비 작업은 계속할 수 있다. 호출자가 QualityReview의 판정과 필수 구현 검사 결과를 확인해 다음 단계로 넘긴다.

## 한 번에 현재 과제 하나

4. 구현 전 기준 커밋과 staged·unstaged·untracked 작업파일 스냅샷을 기록한다. 비Git·재개 상황에서 변경 기준을 복원할 수 없으면 관련 현재 파일 전체를 검토 범위로 정한다. `ready` 과제를 `implementing`으로 바꾼다. 해커톤·시험 대비에서 서브 에이전트를 사용할 수 있으면 [현재 작업의 TDD 위임](references/hackathon.md#현재-작업의-tdd-위임)에 따라 **현재 과제 하나**를 전담 서브 에이전트에게 맡긴다. 다른 모드, 서브 에이전트 부재, 사용자 지정 수행 방식에서는 현재 에이전트가 구현한다. 어느 쪽이든 확정된 과제·지도 버전과 검증 경계, 관련 개념 정의·규칙·출처의 원본 위치를 수행자에게 전달한다.
5. 수행자는 `tdd`를 읽고 합의한 공개 인터페이스에서 **테스트 작성 → 실제 실패 확인 → 최소 구현 → 실제 통과 확인**을 하나씩 반복한다. 기대값은 요구·업무 규칙에서 도출한다. 실행 환경 오류는 기능의 Red와 구분한다. 사용자는 구현 전에 합의한 현재 작업의 지도·결정 이유를 읽는다. 현재 에이전트는 같은 작업의 E2E 입력·환경을 준비할 수 있다. 구현 중 고객 정책의 새 빈틈이나 충돌이 드러나면 수행자는 관련 요구·질문을 호출자에게 반환하고, 호출자는 `task-customer-interview`로 확인한다. 범위·인터페이스·핵심 결정이 바뀌면 구현을 멈추고 과제·지도·합의를 갱신해 사용자에게 알린 뒤 재개한다. 일반적인 Red/Green 결과와 실제 코드 경로는 인계 때 계획과 대조해 기록한다.
6. 현재 에이전트가 수행자의 코드·실행 로그를 직접 확인하고 TaskPacket의 ImplementationChecks에 정한 lint·타입·빌드·단위/통합·영향받는 회귀 검사를 실행한다. 각각의 수행 결과와 미실행·적용 제외 이유를 기록한다. `task-maps`로 실제 코드·결정 ID·검증 근거와 지도를 맞춘 뒤 `task-quality-review`의 `code` 모드에 구현 전 기준·현재 파일·요구·고객 답변·작업·지도를 전달한다. 커밋 전 변경을 포함한 코드와 호출 경로, 계획·실제 코드의 차이를 검토하고 주요 지적은 위 수정 절차로 해결한다. 수정 뒤 영향받는 검사·리뷰·지도를 다시 확인한다. `task-evidence`의 `handoff` 모드에 현재 식별값과 QualityReview·ImplementationChecks·실행 근거를 전달한다. 해커톤 모드에서는 `task-review`로 현재 기능의 실제 동작·결정·검증 대기 상태를 누적 문서에 반영한다. 누락·실패·버전 불일치는 해당 과제에서 해결한다.
7. handoff 결과가 준비되면 `awaiting_joint_e2e`로 기록하고 사용자에게 다음을 보고한 뒤 이번 구현 실행을 끝낸다.
   - 구현한 동작과 선택 이유
   - 실제 Red/Green·필수 구현 검사·설계/코드 리뷰 근거와 남은 항목
   - 두 지도의 변경점과 현재 위치
   - 지금까지의 결정·검증·복습을 읽을 `review.md`
   - 함께 실행할 E2E 입력·행동·기대 결과 및 미검증 범위

   이 상태의 표시명은 **구현 완료·공동 검증 대기**다. 모든 인수 기준의 검증 완료나 다음 과제 착수로 해석하지 않는다.

## 공동 E2E와 다음 과제

8. 사용자와 현재 산출물의 실제 경로를 확인한다. 검증 중 정책의 기대값이 모호하거나 답변과 충돌하면 `task-customer-interview`로 다시 확인하고 [고객 확인 결과 적용과 재개](#고객-확인-결과-적용과-재개)에 따라 기준을 갱신한다. 허용된 환경의 UI·API·CLI 중 실제 진입점으로 입력하고 필요한 저장·조회·출력까지 관찰한다. 브라우저가 없는 서버에서는 [서버 미리보기 절차](../contracts/server-preview.md)로 지도와 앱 주소를 구분해 전달하고, 사용자 수동 E2E·자동 브라우저 E2E의 수행 여부를 별도로 확인한다. `task-evidence`의 `joint-e2e` 모드로 실행 근거와 사용자의 결과 확인을 정리한다.
9. [상태 전이](../contracts/task-workflow-v1.md#상태-전이)에 따라 현재 과제를 처리한다. 실패는 같은 과제의 `fixing`, 환경·근거 부족은 `blocked`로 두고 원인을 해결한다. 해커톤 모드에서 공동 E2E가 실패하거나 막히면 `task-review`로 `review.md`에도 그 상태를 반영한다. `awaiting_joint_e2e`에서 기다리는 것은 정상 협업 상태다.
10. 현재 버전의 필수 E2E 통과·사용자 결과 확인과 함께, 적용되는 QualityReview·ImplementationChecks의 유효한 결과 및 미해결 주요 결함 없음을 확인한 경우 `verified`로 바꾼다. 해커톤·시험 대비 모드에서는 여기서 짧은 자기 설명을 요청하고 사용자 응답을 기다린다. `task-evidence`의 `learning-review`로 현재 과제에 설명·막힌 부분·복습 지점을 남기고, `task-review`로 기능 상태·실제 사용자 설명·다음 대화 지점을 누적 문서에 갱신한다. 답변을 명시적으로 보류했다면 그 상태를 그대로 표시한다. 다음 기능으로 넘어가는 조건과 명시적 보류는 [자기 설명 절차](references/hackathon.md)를 따른다.
11. `task-maps`로 전체 지도에 기능 검증 결과와 변경된 복습 표시를 반영하고 의존관계가 풀린 다음 과제 하나의 패키지를 보여준다. 이미 합의된 범위·검증 지점은 재사용하고 새 결정이 있는 부분만 확인한다. 마지막 과제까지 검증되면 제출 요구별 근거와 실행 방법을 인계한다. 해커톤·시험 대비에서는 `task-review`로 `review.md`에 전체 경로·핵심 절충·남은 복습과 실제 결정에 근거한 인터뷰 연습 질문을 모아 사용자가 자기 말로 답해 볼 수 있게 한다.

재개 시 `plan.md`가 참조하는 개념·규칙의 정본과 고객 질문·답변·출처·확인 시점을 읽고 새 답변을 해당 질문 ID에 연결한다. 재개하는 현재 작업에 품질 정책·검사 목록을 보완하고 이전 테스트·리뷰 뒤 코드·기준이 달라졌는지 확인한다. 달라진 부분의 통과 근거를 다시 확보한다. 과거 완료 기록은 당시 근거로 보존하고 다시 연 작업에 현재 정책을 적용한다. 사용자의 단순한 “계속”만으로 공동 E2E 통과를 기록하지 않는다. 커밋·외부 이슈 게시·실제 제출은 이 스킬의 자동 부수 작업이 아니다.
