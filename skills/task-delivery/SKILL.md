# 한 서브 과제씩 검증하며 진행하기

사용자와 에이전트가 같은 과제·객체 지도·흐름 지도를 읽는다. 이 스킬은 도구를 조합하고 작업 상태를 관리한다. 실제 함수 호출이나 백그라운드 실행 엔진이 아니라, 코딩 에이전트가 따라 실행하는 절차다.

시작할 때 [공유 계약](../contracts/task-workflow-v1.md)을 읽고, 사용할 기능에 해당하는 [구성 요소](../contracts/components.md)를 확인한다. 분석·지도 작성만 요청했다면 그 범위까지만 수행한다. 실제 시험에서는 확인된 허용 도구·행동 범위가 우선이다.

해커톤·시험 대비로 진행할 때는 [시간 배분과 자기 설명 절차](references/hackathon.md)를 읽는다. 이 모드에서는 기능 검증 뒤 사용자 설명을 받고 이해가 막힌 부분을 기록한 다음 다음 기능으로 넘어간다.

## 시작 또는 재개

1. 과제 원문·제출 요구·기존 코드와 작업 기록을 읽는다. 기존 `.workflow/<과제명>/`이 있으면 실제 코드와 대조해 이어받는다. 새 기록은 아래 구조를 사용하되 같은 역할의 기존 파일이 있으면 재사용한다.

   ```text
   .workflow/<과제명>/
     plan.md                 전체 구현 방향·결정 이유·작업 순서·복습 색인
     tasks/T01.md             현재 상태의 원본, 한 파일에 한 과제
     maps/index.md            두 지도 버전·코드 근거·노드 색인
     maps/objects.mmd         객체·책임·인터페이스
     maps/flow.mmd            입력부터 결과까지의 실행 경로
     maps/view.html           사용자가 읽는 지도
     evidence/T01/            시도별 handoff·joint-e2e·실행 근거
   ```

2. [전체 구현 양식](assets/plan.md)을 참고해 `plan.md` 초안을 먼저 만든다. 원문·기존 코드에서 확인할 수 있는 사실과 요구 ID를 정리하고, `to-tickets`의 분해 기준으로 입력부터 결과까지 확인 가능한 작은 기능의 순서·의존관계·인수 기준을 잡는다. 해커톤 모드의 독립 조사 병렬화와 결과 합치기는 [해커톤 절차](references/hackathon.md#병렬-준비와-한-기능-집중)를 따른다. **분해와 함께** 구조·상태·동시성·실패 처리 등 작업 경계나 정합성에 영향을 주는 기술적 갈림길을 찾는다. 뒤 작업의 요구가 현재 작업의 저장 구조·처리 순서를 바꾸는지도 확인한다. 중요한 것에는 결정 ID, 관련 요구·작업, 선택지의 득실, 추천과 이유, 아직 확인할 점을 적어 전체 순서와 함께 사용자에게 보여준다. `task-design-dialogue`로 사용자와 질문·반론·수정안을 왕복하며 현재 구현에 필요한 결정을 정한다. 원문 요구, 사용자와 합의한 결정, AI 제안, 남은 가정을 구분한다. 현재 과제부터 상세화하고 후속 과제는 개요로 둔다. 이미 합의한 결정과 분해는 재사용한다. 공유 문서의 설명 문장은 [simple-english 문서 어댑터](../contracts/components.md#simple-english-문서-어댑터)로 점검한다. 해커톤에서 논의할 선택의 우선순위는 [해커톤 절차](references/hackathon.md)를 따른다.
3. [과제 양식](assets/task.md)으로 현재 과제 하나를 구체화하고 전체 계획의 요구 ID·결정 ID를 참조한다. `task-maps`로 객체·흐름 지도를 만들고 인수 기준을 관찰할 공개 인터페이스와 결정이 영향을 주는 책임·경계를 표시한다. HTML에는 작업별 기록을 두고 현재 작업의 예정 구현 경로·선택 이유·검증 지점을 **TDD 시작 전에** 읽을 수 있게 한다. 후속 작업은 개요와 계획 상태로 둔다. 사용자가 검토할 패키지는 과제·두 지도·결정 요약·TDD 검증 지점·E2E 경로다. **해당 과제의 범위와 검증 지점이 합의되고 선행 작업이 검증 완료일 때** `ready`로 둔다. 현재 구현을 바꾸는 중요한 미결정 사항은 선택지와 영향을 보여준 뒤 먼저 해결한다. 나중 작업에만 필요한 선택은 제안 상태로 두고, 사소한 내부 선택은 근거를 적은 가정이나 에이전트 판단으로 진행할 수 있다. 사용자가 판단을 맡기면 에이전트 선택으로 기록한다. 일반적인 진행 동의를 아직 제시하지 않은 선택의 합의로 기록하지 않는다.

## 한 번에 현재 과제 하나

4. `ready` 과제를 `implementing`으로 바꾼다. 해커톤·시험 대비에서 서브 에이전트를 사용할 수 있으면 [현재 작업의 TDD 위임](references/hackathon.md#현재-작업의-tdd-위임)에 따라 **현재 과제 하나**를 전담 서브 에이전트에게 맡긴다. 다른 모드, 서브 에이전트 부재, 사용자 지정 수행 방식에서는 현재 에이전트가 구현한다. 어느 쪽이든 확정된 과제·지도 버전과 검증 경계를 수행자에게 전달한다.
5. 수행자는 `tdd`를 읽고 합의한 공개 인터페이스에서 **테스트 작성 → 실제 실패 확인 → 최소 구현 → 실제 통과 확인**을 하나씩 반복한다. 기대값은 요구·업무 규칙에서 도출한다. 실행 환경 오류는 기능의 Red와 구분한다. 사용자는 구현 전에 합의한 현재 작업의 지도·결정 이유를 읽는다. 현재 에이전트는 같은 작업의 E2E 입력·환경을 준비할 수 있다. 범위·인터페이스·핵심 결정이 바뀌면 구현을 멈추고 과제·지도·합의를 갱신해 사용자에게 알린 뒤 재개한다. 일반적인 Red/Green 결과와 실제 코드 경로는 인계 때 계획과 대조해 기록한다.
6. 현재 에이전트가 수행자의 코드·실행 로그를 직접 확인하고 영향을 받는 회귀 검사를 실행한다. 선택한 방식이 실제 코드에 어떻게 반영됐는지와 예상한 절충·한계를 대조한다. `task-maps`로 실제 코드·결정 ID·검증 근거와 지도를 맞춘다. `task-evidence`의 `handoff` 모드에 현재 과제·지도·코드 식별값과 실행 근거를 전달한다. 누락·실패·버전 불일치는 해당 과제에서 해결한다.
7. handoff 결과가 준비되면 `awaiting_joint_e2e`로 기록하고 사용자에게 다음을 보고한 뒤 이번 구현 실행을 끝낸다.
   - 구현한 동작과 선택 이유
   - 실제 Red/Green·관련 회귀 근거
   - 두 지도의 변경점과 현재 위치
   - 함께 실행할 E2E 입력·행동·기대 결과 및 미검증 범위

   이 상태의 표시명은 **구현 완료·공동 검증 대기**다. 모든 인수 기준의 검증 완료나 다음 과제 착수로 해석하지 않는다.

## 공동 E2E와 다음 과제

8. 사용자와 현재 산출물의 실제 경로를 확인한다. 허용된 환경의 UI·API·CLI 중 실제 진입점으로 입력하고 필요한 저장·조회·출력까지 관찰한다. `task-evidence`의 `joint-e2e` 모드로 실행 근거와 사용자의 결과 확인을 정리한다.
9. [상태 전이](../contracts/task-workflow-v1.md#상태-전이)에 따라 현재 과제를 처리한다. 실패는 같은 과제의 `fixing`, 환경·근거 부족은 `blocked`로 두고 원인을 해결한다. `awaiting_joint_e2e`에서 기다리는 것은 정상 협업 상태다.
10. 현재 버전의 필수 E2E가 통과하고 사용자가 결과를 확인한 경우만 `verified`로 바꾼다. 해커톤·시험 대비 모드에서는 여기서 짧은 자기 설명을 요청하고 사용자 응답을 기다린다. `task-evidence`의 `learning-review`로 현재 과제에 설명·막힌 부분·복습 지점을 남긴다. 다음 기능으로 넘어가는 조건과 명시적 보류는 [자기 설명 절차](references/hackathon.md)를 따른다.
11. `task-maps`로 전체 지도에 기능 검증 결과와 변경된 복습 표시를 반영하고 의존관계가 풀린 다음 과제 하나의 패키지를 보여준다. 이미 합의된 범위·검증 지점은 재사용하고 새 결정이 있는 부분만 확인한다. 마지막 과제까지 검증되면 제출 요구별 근거와 실행 방법을 인계한다. 해커톤·시험 대비에서는 남은 복습 지점도 함께 연결한다.

재개 시 이전 테스트 뒤 코드·기준이 달라졌는지 확인한다. 달라진 부분의 통과 근거를 다시 확보한다. 사용자의 단순한 “계속”만으로 공동 E2E 통과를 기록하지 않는다. 커밋·외부 이슈 게시·실제 제출은 이 스킬의 자동 부수 작업이 아니다.
