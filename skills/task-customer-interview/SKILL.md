# 고객의 업무 정책을 확인하기

입력은 원본 요구·코드 근거·`plan.md`·현재 작업·기존 질문과 답변이다. 출력은 계획의 고객 확인 기록, 요구·인수 기준 변경 요약, 남은 질문이다. [CustomerInterviewNote](../contracts/task-workflow-v1.md#customerinterviewnote--고객-정책-확인의-선택-확장)를 따른다.

단독 요청에서는 제공된 요구·대화부터 분석한다. 계획이나 작업 ID가 아직 없으면 연결 대상을 미정으로 두고 결과를 제공한다. 기록을 요청받으면 기존 계획을 재사용하거나 최소 `plan.md`를 만든다. 기술 선택은 [task-design-dialogue](../task-design-dialogue/SKILL.md), 구현 뒤 자기 설명·복습은 `task-evidence`·`task-review`로 연결한다.

## 확인할 정책 찾기

1. 원문·문서·코드·이전 답변을 읽고 확인된 요구, 현재 코드의 동작, 고객에게 확인할 정책, 기술 선택을 구분한다. 적용 범위가 같은 기존 답변은 출처와 함께 재사용한다.
2. [개념·규칙·출처 기본 점검](../contracts/task-workflow-v1.md#개념과-규칙의-출처-연결)에 따라 권한·데이터 소유권·업무 순서·상태 전이·실패와 복구·성공 조건을 살핀다. 결과를 바꾸는 주요 용어의 대상·범위와 관계를 확인한다. 예를 들어 ‘사용자당 한 번’의 중복 기준이 계정인지 사람인지 불명확하면 실제 사례로 질문한다. 답에 따라 현재 기능의 동작이나 인수 기준이 달라지는 질문부터 고른다. 후속 기능에만 필요한 질문에는 해당 작업과 확인 시점을 붙인다.
3. 각 질문에 `Q01` 같은 안정적인 ID, 관련 요구·작업·인수 기준, 질문 이유와 달라질 동작을 붙인다. 확정 요구는 원문으로 연결하고, 미확인 정책은 열린 질문으로 남긴다.

## 질문하고 답변 받기

4. 지금 필요한 쟁점 하나를 실제 업무 상황으로 묻는다. 현재 처리 방식이나 최근 사례를 먼저 확인하고, 답이 추상적이면 경계 조건·예외·관찰할 결과를 구체화한다. 선택지를 제시할 때는 중립적으로 구성하고 고객의 별도 설명이나 담당자 확인 필요도 받을 수 있게 한다.
5. 기본 경로는 사용자가 고객사 담당자·챗봇에 질문을 전달하고 답변을 가져오는 방식이다. 복사할 질문과 짧은 배경을 제공한다. 직접 대화는 사용자가 해당 상대와의 대화를 맡겼고 접근 수단·허용 범위가 확인된 경우에 수행한다.
6. 질문을 작성한 시점에는 `open`으로 둔다. 고객에게 전달한 근거가 있을 때 `waiting`으로 바꾸고 전달 경로를 남긴다. 사용자에게 질문 초안을 보여준 사실과 고객에게 실제로 물은 사실을 각각 기록한다.
7. 받은 답을 짧게 되짚고 실제 답변·출처·응답 주체·적용 범위를 기록한다. 해석은 별도 항목으로 둔다. 대회가 제공한 고객봇 답변에는 그 출처를, 에이전트가 만든 연습 응답에는 가상 예시임을 표시한다. 부분 답변은 해결된 조건과 남은 조건을 나누어 후속 질문에 연결한다.

고객 정책은 적용 가능한 문서·담당자 답변으로 확인한다. 일반 관행과 AI 추천은 가정으로 표시한다. 사용자가 정책을 정할 권한을 갖고 새 규칙을 결정했다면 결정 주체·범위·근거를 남긴다. “알아서 해줘”만 받은 고객사 고유 정책은 미확인 상태로 두고, 위임받은 기술 판단은 설계 결정으로 기록한다.

## 답변을 요구와 검증에 연결하기

8. 답변에서 확인한 개념의 의미·적용 범위와 관찰 가능한 업무 규칙의 조건·예외를 기존 요구·질문에 정리하고, 정본 참조와 연결된 작업·인수 기준의 변경안을 만든다. 원문이 정한 조건과 답변이 충돌하면 두 출처와 적용 범위를 보존하고 `conflict`로 둔다. 정정 권한·적용 시점을 확인해 해소한다.
9. 질문의 필요한 조건이 구체화되고 근거와 반영 대상·변경안이 연결되면 `resolved`로 둔다. 후속 작업까지 확인을 미룰 수 있는 항목은 `deferred`와 필요한 시점을 기록한다. 현재 기능의 필수 기대값을 바꾸는 미해결 조건은 호출자에게 드러낸다.
10. 정정 답변은 같은 질문 ID의 이력에 덧붙인다. 영향을 받는 요구·인수 기준·작업과 기존 검증을 찾아 변경 요약에 포함한다. 호출자가 계획·작업·지도 버전을 맞추고 필요한 검증을 다시 수행할 수 있게 한다.

현재 기능의 중요한 정책과 기대 결과가 구체화되면 인터뷰 결과를 반환한다. 남은 질문에는 다음 확인 시점을 붙인다. 응답이 오면 저장된 질문·답변·적용 범위를 읽고 해당 쟁점부터 재개한다.

## 호출자에게 반환하기

[ToolResult](../contracts/task-workflow-v1.md#toolresult)에 실제 기록 위치와 확인 근거를 담는다. 정상적으로 질문·분석 결과를 산출했다면 `status`는 `ok`이고 `verdict`는 다음 중 하나다.

- `ready` — 현재 범위의 중요한 정책과 기대 결과가 구체화되어 반영할 변경을 전달할 수 있음.
- `awaiting_answers` — 질문이 준비됐거나 전달되어 고객 답변이 필요함. 질문별 전달 상태와 필요한 시점을 함께 반환.
- `needs_clarification` — 답변이 모호하거나 출처가 충돌하여 추가 확인이 필요함.

필요한 원문을 읽을 수 없거나 요청된 기록 저장이 실패했다면 `status: blocked`와 원인을 반환한다. 고객 답변 대기는 정상 인터뷰 결과로 기록한다. 작업 상태·구현·검증 판정은 호출자인 `task-delivery`가 담당하며, 단독 실행에서는 사용자가 요청한 질문·답변 정리 범위까지 수행한다.
