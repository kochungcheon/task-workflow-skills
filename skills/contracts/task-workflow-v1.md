# 과제 협업 산출물 계약 v1

이 파일은 도구와 자동화 양쪽이 읽는 공유 형식이다. Markdown에 아래 이름을 필드 또는 표 열로 유지한다. 필수 정보의 의미가 바뀌면 계약의 주 버전을 바꾸고 [구성 요소·호출자](components.md)를 함께 확인한다.

## 공통 식별값

- `contract_version`: `1`.
- `task_id`, `task_revision`: 어떤 요구 버전의 작업인가. 기준·검증 경계 변경 시 task_revision을 올린다.
- `map_revision`: 사람이 보는 HTML과 에이전트 원본이 공유하는 지도 버전.
- `code_ref`: 확인한 코드 상태. 커밋만으로 표현할 수 없는 작업 파일은 관련 파일의 경로·내용 해시 목록 등 재식별 가능한 근거를 포함한다. 시간만으로 코드 버전을 대신하지 않는다.

## TaskPacket

원본은 `tasks/<task_id>.md`. [양식](../task-delivery/assets/task.md)을 복사해 실제 내용으로 채운다.

필수 정보: 과제 원문 위치, 하나의 관찰 가능한 목표, 제외 범위, `blocked_by`, 인수 기준 ID별 입력·행동·기대 결과, 관련 실패 조건, 합의한 공개 테스트 인터페이스, 실제 E2E 경로, 두 지도 경로와 관련 노드 ID, 사용자 합의 근거, 현재 상태와 증거 링크.

`plan.md`는 전체 구현 방향과 작업 순서의 원본이다. 상태를 재표시한다면 각 TaskPacket의 값으로 갱신한다. 의존관계가 순환하거나 기준이 충돌하면 구현 전에 해소한다. 새 컨텍스트에서 이 패키지만으로 시작할 수 없을 만큼 큰 기능은 더 자른다.

## PlanNote · 대화 기반 계획의 선택 확장

새 과제는 [전체 구현 양식](../task-delivery/assets/plan.md)을 참고한다. 원본 요구 위치·요구 ID, 목표·제외 범위·완료/제출 기준, 핵심 구조, 결정 ID·선택 이유·합의 근거, 남은 가정, 작은 기능의 순서·의존관계를 `plan.md`에 둔다. 제안·합의·가정을 구분하고 실재하지 않은 사용자 판단을 만들지 않는다.

해커톤·시험 대비에서는 티켓 분해와 함께 작업 경계·정합성 등에 영향을 주는 기술적 선택을 찾는다. 원문·코드 등에서 확인되는 사실은 출처와 함께 조사하고, 사용자에게는 여러 타당한 방향 중 선택할 결정을 초안과 함께 보여준다. 결정 항목에는 질문, 실제로 검토한 선택지의 득실·적용 조건, 추천 또는 선택 이유, 사용자 합의/에이전트 선택/미확인 상태, 관련 요구·작업·지도 노드, 구현 뒤 코드·검증 근거를 연결한다. 아직 대화하지 않은 대안이나 사용자 결정을 만들어 채우지 않는다. 현재 작업에 영향을 주는 미결정 사항은 구현 전에 해결하고 후속 작업 항목은 해당 시점까지 제안으로 둘 수 있다. 영향이 작거나 후속 작업에만 필요한 미확인점은 가정 ID·반영 위치·영향·확인 시점을 기록한다.

`task-design-dialogue`는 이 결정 항목을 사용자와 왕복해 채우는 도구다. 결과는 별도 PRD가 아니라 같은 `plan.md`와 호출자에게 전달하는 작업·지도·검증 변경 요약이다. 대화가 계속되면 미확인 상태를 보존한다. 이 도구는 `ready` 판정이나 지도·코드 수정을 맡지 않는다.

`plan_revision`은 계획·결정 변경 때 올린다. 작업 MD는 전체 계획 경로·참조 버전·관련 요구/결정 ID를 연결한다. 변경된 요구·결정의 영향을 받는 작업·지도·검증 기준을 갱신하고, 범위·검증 경계·선택 이유가 바뀐 작업의 `task_revision`도 올린다. 현재 작업만 완전한 TaskPacket으로 상세화하고 후속 작업 개요는 계획에 둔다. 기존 v1 과제에는 필요한 연결만 보완할 수 있으며 기존 Evidence·상태 전이의 필수 의미는 유지한다.

### 개념과 규칙의 출처 연결

새 작업과 재개하는 현재 작업의 분석·리뷰에서 기본으로 점검한다. 구현 결과를 바꾸는 주요 용어가 가리키는 대상·역할·관계와 업무 규칙의 조건·예외·출처를 요구·인수 기준과 대조한다. 예를 들어 ‘사용자당 한 번’의 사용자가 계정인지 사람인지에 따라 중복 검사 기준이 달라질 수 있다.

- 의미가 모호해 기대 결과가 달라지거나, 여러 작업이 공유하는 규칙의 해석이 갈리거나, 출처 충돌·정정이 있으면 필요한 기록을 보완한다. 기존 기록으로 의미와 기대 결과가 명확하면 그 기록을 재사용한다.
- 용어 정의는 프로젝트의 기존 용어집·도메인 문서에서 해당 업무 범위에 맞는 정본을 참조한다. 정본이 없으면 `plan.md`의 관련 요구·고객 질문에 짧게 적는다. 업무 문맥별 의미가 다르면 적용 범위를 붙여 구분한다. 규칙의 조건·예외·출처·현재 확정 상태는 기존 `R`·`Q`와 연결하고 인수 기준·검사에서 같은 항목을 참조한다. 기술 선택은 기존 `D`, 가정은 기존 가정 기록에 둔다.
- 필요한 기록은 정의·구분 또는 규칙, 적용 범위, 근거 원문/답변과 상태, 영향받는 요구·작업·인수 기준이다. 단순한 항목은 관련 행에 한두 문장으로 남긴다. 여러 작업의 공통 정의가 쌓이면 같은 `plan.md`에 한 곳으로 모으고 각 사용처는 원본을 참조한다.
- 고객 고유 정책의 미확정점은 `CustomerInterviewNote`의 질문으로 연결한다. 원문 요구·실제 답변·코드에서 관찰한 동작·에이전트 가정은 각각의 근거와 상태를 유지한다. 현재 작업의 필수 기대값을 정할 수 없는 경우 기존 질문 대기·차단·재개 규칙을 적용하고, 후속 작업의 질문에는 확인 시점을 붙인다.
- 현재 작업 패키지와 구현 위임·독립 리뷰 입력에 관련 정의·규칙의 정본 위치와 적용 버전을 연결한다. 지도와 복습 문서는 현재 동작에 필요한 의미·범위를 원본 링크로 요약한다. 설계 리뷰는 해석과 기대값, 코드 리뷰와 실행 검사는 실제 동작을 같은 근거에 대조한다.
- 정정이 오면 호출자인 `task-delivery`가 원본과 영향받는 요구·작업·인수 기준·지도를 갱신하고 기존 버전 규칙에 따라 리뷰·검증을 다시 확인한다. 이전 답변과 실행 근거는 당시 버전의 이력으로 보존한다.

이 점검은 기존 PlanNote·CustomerInterviewNote·TaskPacket·QualityReview의 기록과 상태 전이를 사용한다. 점검과 필요한 기록은 현재 분석·인터뷰·리뷰 단계 안에서 수행한다.

## CustomerInterviewNote · 고객 정책 확인의 선택 확장

고객의 업무·정책·예외를 확인할 때 `plan.md`에 추가하는 기록이다. [task-customer-interview](../task-customer-interview/SKILL.md)가 질문과 답변 근거를 정리하고, `task-delivery`가 작업·지도·검증 기준에 적용한다. 기존 v1 기록은 필요한 질문이 생길 때 이 항목을 추가한다. 기록이 없다는 사실만으로 과거 고객 확인을 추정하지 않는다.

각 질문은 안정적인 `Q01` 같은 ID, 확인할 정책과 질문 이유, 관련 요구·작업·인수 기준, 응답자·출처·적용 범위, 실제 답변 또는 원문 참조, 에이전트 해석·반영할 변경, 상태·다음 확인 시점을 갖는다. 작업이 정해지기 전의 작업·인수 기준 ID는 미정으로 두고 분해할 때 연결한다. 기존 코드의 동작, 문서의 요구, 고객 답변, 정책 결정권자의 새 결정, 에이전트 제안을 구분한다. 연습용 가상 응답은 가상 예시로 표시한다.

| 질문 상태 | 의미 |
|---|---|
| `open` | 질문 초안 또는 추가 확인이 필요한 항목. 실제 전달 근거는 아직 없음 |
| `waiting` | 응답자에게 질문이 전달된 근거가 있고 답변 대기 중 |
| `resolved` | 필요한 정책·조건이 출처와 함께 구체화됐고 요구·인수 기준의 반영 대상과 변경안이 연결됨 |
| `deferred` | 후속 작업에서 확인할 항목. 영향과 해당 작업 착수 전 등 확인 시점이 기록됨 |
| `conflict` | 출처·답변 간 충돌이 남아 두 근거와 확인할 주체가 기록됨 |

답변 정정은 이전 답변·출처를 보존하고 같은 질문을 다시 열어 변경 이유를 덧붙인다. `task-delivery`는 요구·기대값이 달라지면 `plan_revision`과 영향받는 `task_revision`을 올리고 과제·지도·검증 지점을 맞춘다. 기존 통과 근거는 해당 버전의 이력으로 보존하고 영향받는 검사를 다시 수행한다. 이미 `verified`인 작업도 아래 상태 전이에 따라 다시 연다.

질문을 정상 정리한 도구 결과는 `status: ok`로 반환한다. `verdict`는 현재 범위의 정책과 반영안이 준비된 `ready`, 필요한 답변을 기다리는 `awaiting_answers`, 모호한 응답이나 충돌이 남은 `needs_clarification`이다. 각 결과에 미해결 질문 ID·영향받는 작업·변경 요약을 연결한다. 인터뷰의 `ready`는 작업의 상태 판정과 별개다. 도구 실행에 필요한 자료를 읽거나 기록할 수 없는 경우에는 원인과 함께 `status: blocked`를 반환한다.

질문 대기는 항목별로 기록한다. 현재 작업의 구조·필수 인수 기준을 결정할 수 없는 실제 원인이 있을 때 호출자가 해당 작업에 `blocked`, 질문 ID·영향, `resume_state`를 기록한다. 후속 작업 질문은 확인 시점을 연결하고 현재 작업에서 독립적인 조사·환경 준비는 진행할 수 있다. 답변 수신 뒤 반영된 과제·지도·검증 경계와 기존 합의를 대조한 다음 원래 진행 단계로 재개한다.

## QualityReview · 설계·코드 검토의 선택 확장

`quality_policy: review-v1`인 TaskPacket에 적용한다. 새 작업과 재개하는 현재 작업에 이 정책과 필요한 검사를 기록한다. 기존 완료 작업의 근거는 당시 정책으로 보존하고, 해당 작업을 다시 열면 현재 정책을 적용한다. 정책이 없는 과거 v1 기록의 필드와 상태 의미는 유지한다.

[task-quality-review](../task-quality-review/SKILL.md)는 `design`과 `code` 모드로 검토하고 `evidence/<task_id>/<mode>-review-<시도>.md`에 결과를 반환한다. 현재 범위의 권한·상태 전이·데이터 정합성·공개 인터페이스·동시성·실패 복구를 바꾸는 중요한 선택에는 설계 리뷰가 필요하다. 단순하고 이미 명확한 작업은 이유와 함께 설계 리뷰를 `not_applicable`로 기록할 수 있다. 코드 변경에는 코드 리뷰를 수행하며, 코드 변경이 없는 작업은 해당 범위와 이유를 적는다.

기록에는 다음 정보를 둔다.

- `review_id`, `mode`, `reviewed_refs`에 계획·작업·지도·코드 식별값과 실제 읽은 입력 파일을 기록한다.
- `review_scope`에 요구·인수 기준·대상 파일·관련 호출 경로, `change_basis: diff | current_files`와 기준을 기록한다. `diff`는 기준 커밋과 작업 시작 전의 staged·unstaged·untracked 파일 스냅샷을 현재 파일과 대조한다. 스냅샷에는 복원 가능한 본문 또는 패치와 해시를 둔다. 기존 사용자 변경과 이번 작업 변경을 구분한다. 기준을 복구할 수 없으면 관련 현재 파일 전체를 검토하는 `current_files`로 범위를 명시하고 변경 귀속은 미확인으로 남긴다.
- `reviewer_id`, `reviewer_mode: independent | self`, `independence_required`와 실행·완료 근거를 기록한다. 설계 리뷰는 이전 대화를 전달받지 않은 독립 리뷰어가 수행한다. 코드 리뷰도 가능한 환경에서는 독립 리뷰어가 수행하며, 지원되지 않을 때 `self`와 한계를 명시할 수 있다. 요구된 독립 검토를 수행하지 못했거나 입력을 읽지 못한 결과는 `not_run`이다.
- `findings`에는 안정적인 ID, `severity: blocker | major | minor`, 위치·관련 요구, 발생 조건·영향·근거, `disposition: open | fixed | dismissed | accepted_risk`, 처리 이유·재검토 근거를 둔다. `fixed`는 수정 후 해당 문제와 영향받는 검사를 확인한 상태다. `dismissed`는 요구·코드 근거로 지적이 성립하지 않음을 설명한다. `accepted_risk`는 판단 주체·영향·후속 조치를 기록하며 필수 인수 기준 위반이나 확인된 주요 결함의 통과 근거로 사용할 수 없다.
- `verdict`는 `pass | needs_work | not_run | not_applicable`이다. `pass`에는 현재 범위의 검토 완료와 blocker·major의 수정 확인 또는 근거 있는 기각이 필요하다. 미해결 주요 지적은 `needs_work`, 수행 불가는 `not_run`으로 남긴다. `not_applicable`에는 적용 대상이 없는 이유가 필요하다.

리뷰어는 검토 자료를 읽고 지적을 반환한다. 호출자가 정책 공백을 고객 인터뷰, 기술 선택을 설계 대화, 구현 결함을 현재 과제의 수정으로 연결한다. 기본 한 차례 검토 후 주요 수정과 영향을 받은 범위를 재검토한다. 횟수·시간 소진 시 미해결 항목과 다음 조치를 기록한다. 리뷰 결과만으로 작업 상태를 바꾸거나 실행 검사의 통과를 만들지 않는다.

계획·정책·코드 변경 뒤에는 영향받는 리뷰를 다시 확인한다. 문서 표현만 바뀐 경우에는 기존 근거의 적용 범위를 대조해 재사용 이유를 남길 수 있다. 리뷰 중 입력이 바뀌면 새 식별값으로 필요한 검토를 완료한 뒤 판정한다.

### ImplementationChecks

같은 정책의 구현 검사 목록을 현재 TaskPacket에 먼저 정하고 handoff에 실제 결과를 연결한다. 저장소의 검사 명령·CI·요구사항에서 적용되는 lint·타입·빌드·단위/통합·회귀 검사를 선택하고 각 항목의 `required` 여부와 이유를 기록한다. 언어나 프로젝트에 적용되지 않는 종류는 이유와 함께 `not_applicable`로 둔다.

각 결과에 `check_id`, 종류, 명령·수행자, `code_ref`, 기대·실제 결과·근거, `result: pass | fail | not_run | not_applicable`를 남긴다. 실패·도구 부재·실행 생략은 해당 사실대로 기록한다. 요구된 테스트가 0건이거나 관련 테스트가 전부 skip이면 실행 명령의 성공만으로 `pass`를 부여하지 않는다. 필수 검사의 미실행·실패가 해소돼야 인계할 수 있다. 검사 요구를 변경할 때는 원문·프로젝트 기준 또는 실제 사용자 결정과 변경 이유를 남긴다.

이 정책을 적용한 작업의 전이 조건을 아래 기본 상태 전이에 추가한다. `ready`에는 적용되는 설계 리뷰의 현재 `pass` 또는 근거 있는 `not_applicable`이 필요하다. `awaiting_joint_e2e`와 `verified`에는 설계·코드 리뷰의 유효한 결과, 필수 ImplementationChecks 충족, 미해결 주요 결함 없음이 함께 필요하다. 부족한 리뷰·검사 때문에 현재 진행이 막히면 호출자가 원인과 `resume_state`를 기록한다. `verified`에는 기존 공동 E2E 통과와 사용자 확인도 필요하다.

## MapSet

필수 출력: `maps/objects.mmd`, `maps/flow.mmd`, `maps/index.md`, 이 협업에서 사람이 보는 `maps/view.html` 또는 기존 동등 산출물.

- 색인: 공통 식별값, 노드 ID↔코드 위치↔인수 기준, 계획/구현 구분, 변경 요약.
- 객체 지도: 책임, 공개 인터페이스의 입력·출력·오류, 의존 방향.
- 흐름 지도: 진입·처리·저장/외부 경계·결과, 관련 실패 경로, 현재 과제 위치.
- 해커톤·시험 대비 HTML: 작업별 이동과 구현 기록을 제공한다. 현재 작업은 TDD 전의 계획 경로와 검증 지점을 표시해 구현 중 사용자가 읽게 한다. 구조·결정·검증 경계가 바뀌면 계획과 실제의 차이를 표시하고 사용자에게 알린다. 인계 때 실제 코드·검증 근거를 반영하며 `계획`과 `구현` 표시를 구분한다. 후속 작업의 개요는 미구현과 구분한다.
- 해커톤·시험 대비에서 `plan.md`의 중요한 결정 ID를 영향을 받는 객체 지도 노드와 색인에 연결한다. HTML에는 모든 중요한 결정의 상태·선택 이유·대안 조건·관련 노드·실제 검증 근거를 요약하고, 현재 기능의 결정과 반영된 미확인 가정은 첫 화면에 노출한다. 계획을 원본으로 유지하며 제안·합의·에이전트 선택·가정을 섞지 않는다.
- 지도 원본과 HTML은 같은 map_revision을 표시한다. 노드·간선·책임·실행 경로 변경 시 버전을 올리고 현재 과제의 포인터를 갱신한다. HTML만의 배치 변경은 구조 버전을 올릴 필요가 없다.
- 결정 설명·구현 근거·학습 표시만 바뀌고 노드/간선이 동일하면 `plan_revision`과 코드 근거를 맞춰 HTML·색인을 갱신하되 구조의 `map_revision`은 유지할 수 있다.
- 구조가 구현되어도 과제는 아직 E2E 대기일 수 있다. `계획/구현`은 구조 상태, `현재/검증 완료/후속`은 과제 진행 상태다.
- `maps/index.md` 또는 연결된 인계 기록에 미리보기 서버의 실행 명령·제공 디렉터리·포트·재사용 여부와 `preview_internal_url`, `preview_user_url`을 기록한다. 앱·E2E 대상은 별도의 `app_internal_url`, `app_user_url`로 기록한다. 미확인 URL은 미확인으로 둔다. [서버 미리보기 절차](server-preview.md)를 따른다.
- HTML 생성·자산 확인, HTTP 응답, 자동 브라우저 검사, 사용자 화면 확인은 각각 결과·수행자·근거를 기록한다. HTTP `200`은 화면 확인이나 기능 E2E의 통과 근거가 아니다. 브라우저 부재 시 화면 확인은 `pending`으로 두고 지도 생성 자체가 성공했다면 기능 구현 진행을 막지 않는다.

## Evidence

필수 정보: 공통 식별값, 모드, 시도 ID, 인수 기준별 검사 종류·입력·명령/행동·기대·실제 결과·근거 경로, 미검증 범위, `verdict`, `blockers`.

handoff에는 실제 Red/Green 근거·관련 회귀·지도 차이·공동 E2E 시나리오가 필요하다. `quality_policy: review-v1`이면 현재 QualityReview와 ImplementationChecks를 연결하고 위 확장 조건을 확인한다. `verdict`는 `ready_for_joint_e2e | needs_work | blocked`다.

joint-e2e에는 실행 환경, 실제 진입점부터 관찰 결과까지의 범위, 외부 경계 대체 여부, 시나리오별 검사 종류(`manual_user | automated_browser | api_cli` 등)·수행자·결과와 `human_confirmation`이 필요하다. 수동 사용자 E2E와 자동 브라우저 E2E는 별도 시도로 기록하며 서로의 통과를 대체하지 않는다. `verdict`는 `pass | fail | partial | blocked`다. `human_confirmation`은 `pending` 또는 현재 시도·결과에 대한 사용자의 확인 발언/대화 참조다.

근거는 해당 code_ref와 기준 버전에만 유효하다. 이후 변경은 영향을 받는 검사를 다시 수행한다. 지도 표시만 수정했고 코드/기준이 그대로라면 변경 이유와 기존 근거를 연결할 수 있다. 정정은 덧붙여 남기고 이전 시도를 덮어쓰지 않는다.

## LearningNote · 학습 모드의 선택 확장

해커톤·시험 대비에서 `TaskPacket`에 덧붙이는 이해 기록이다. 일반 v1 과제의 필수 필드나 기능 검증의 의미를 바꾸지 않는다. 원본은 `tasks/<task_id>.md`의 이해 기록이며 `plan.md`와 HTML은 이 기록을 연결한다.

기록 항목: 설명 대상의 `task_revision / map_revision / code_ref`, 실제 사용자 설명 또는 발언 참조, 동작 흐름과 선택 이유 각각의 확인 결과, 막힌 부분·오해와 관련 노드/코드, 에이전트 보충, 다시 볼 질문·문서/코드 위치, 재설명 또는 명시적 보류 근거. 이전 설명·막힘·보충을 보존하며 후속 결과를 덧붙인다.

`learning_status`:

- `pending`: 사용자 설명이 없거나 현재 버전의 흐름·선택 이유를 아직 확인하지 못함.
- `explained`: 사용자가 현재 기능의 흐름과 선택 이유를 실질적으로 맞게 설명했고, 확인된 막힘이 남지 않음. 에이전트의 확인 결과이며 시험 통과 보장은 아님.
- `revisit`: 사용자 응답을 받았으나 막힘·오해·설명 누락이 남아 있으며 구체적인 복습 지점을 기록함. 기능 오류가 없다면 학습 모드의 다음 기능 진행은 가능함.
- `deferred`: 사용자가 이번 자기 설명을 명시적으로 보류했고 그 근거와 다음 복습 지점을 기록함. 설명하지 않은 부분은 미확인으로 남음.

`verified`는 기능 검증, `learning_status`는 자기 설명 상태다. 한쪽을 다른 쪽의 증거로 사용하지 않는다. 이 확장을 사용하는 호출자의 시간 배분·응답 대기·재질문·다음 기능 조건은 [해커톤 절차](../task-delivery/references/hackathon.md)를 따른다. 이 확장이 없는 기존 과제는 일반 v1 절차로 재개할 수 있다.

## ReviewBrief · 누적 복습 화면의 선택 확장

해커톤·시험 대비의 `.workflow/<과제명>/review.md`는 `plan.md`·작업 MD·지도·Evidence·LearningNote를 읽기 위한 **파생 요약**이다. [task-review 양식](../task-review/assets/review.md)을 참고한다. 원본 상태를 이 파일에서 새로 판정하지 않는다.

기준 시점과 `plan_revision / map_revision / code_ref`, 요구와 전체 실행 경로, 기능별 구현·공동 E2E·설명 상태, 실제로 택한 중요한 결정과 대안 조건, 확인한 검사·미검증 범위, 사용자와 다시 논의할 질문·실제 답변 상태를 원본 링크와 함께 둔다. 과제 시작·기능 인계·공동 E2E·설명·중요한 설계 변경 뒤 영향받는 부분만 갱신한다. 사실·사용자 발언·AI 요약을 구분하고 오래된 코드 기준의 근거는 현재 검증처럼 표시하지 않는다. 인터뷰 연습 질문은 실제 구현과 결정에서 만든 연습이며 실제 문항 예측이 아니다.

## ToolResult

각 도구가 호출자에게 돌려줄 공통 항목:

```text
contract_version: 1
tool: 수행한 기능 이름
status: ok | blocked
task_id / task_revision / map_revision / code_ref: 해당 식별값
artifacts: 실제 생성·갱신한 파일 경로
checks: 수행한 정합성 확인과 결과
blockers: 부족한 입력·실행 실패·계약 불일치
verdict: 해당 도구가 정의한 결과가 있으면 기입
```

`status: ok`는 도구가 결과를 산출했다는 뜻이다. 실패한 E2E 보고서도 `ok + verdict: fail`로 반환할 수 있다. 과제 통과와 도구 실행 성공을 혼동하지 않는다.

호출자는 상태 전이 전에 contract_version이 기대한 `1`인지, 필수 출력 파일이 존재하는지, 과제·지도·코드 식별값이 현재 입력과 맞는지 확인한다. 필수 필드 누락이나 알 수 없는 버전은 `blocked`로 처리하고 빠진 정보를 드러낸다.

## 상태 전이

상태를 쓰는 주체는 `task-delivery`다. 같은 때 `implementing` 또는 `fixing`인 서브 과제는 하나다.

| 현재 → 다음 | 필요한 근거 |
|---|---|
| `planned → ready` | 범위·검증 인터페이스 합의, 지도 패키지 준비, 모든 선행 과제 verified |
| `ready → implementing` | 현재 과제 선택, 합의한 과제·지도 버전을 읽음 |
| `implementing → fixing` | 현재 코드 리뷰·구현 검사에서 확인한 결함과 같은 과제의 수정 범위 |
| `implementing / fixing → awaiting_joint_e2e` | 현재 코드의 handoff ready_for_joint_e2e, 필수 구현 검사·지도 정합성 충족 |
| `awaiting_joint_e2e → fixing` | 현재 시도의 실제 실패 근거. 요구 변경이면 먼저 과제·지도를 개정 |
| `awaiting_joint_e2e → verified` | 현재 코드·기준의 필수 E2E pass, 사용자 결과 확인, 미해결 필수 기준 없음 |
| 어느 미완료 상태 → `blocked` | 입력·환경·범위·계약 등 진행을 막는 실제 원인과 `resume_state` 기록 |
| `blocked → resume_state` | 원인 해소와 필요한 입력/검사 재확인. verified로 직접 건너뛰지 않음 |
| `verified → planned / fixing` | 기준 변경 또는 실제 회귀 발견 시 기존 근거를 보존하고 작업을 다시 엶 |

인계 후 사용자 응답을 기다리는 상태는 `awaiting_joint_e2e`다. E2E partial/blocked는 검증 완료로 바꾸지 않는다. 단위 테스트만 통과한 경우, 사용자 “계속”만 있는 경우, 코드 버전이 달라진 경우 모두 verified의 조건을 충족하지 않는다.

## 계약 변경

내부 구현만 바뀌면 같은 입력에 필요한 출력·오류 의미가 유지되는지 확인한다. 필수 필드 삭제/이름 변경, 오류 의미 변경은 새 주 버전을 만든다. 기존 주 버전을 사용하는 호출자를 [구성 요소](components.md)에서 찾아 명시적으로 이전하거나 호환 어댑터를 둔다. 최신 버전이라는 이유만으로 자동 대체하지 않는다.

검토 사례: 정상 인계, E2E 실패 후 현재 과제 복귀, 사용자 확인 누락, 오래된 지도/코드, 필수 출력 누락. 문서상 전이 규칙이며 별도 프로그램이 강제하는 상태 기계는 아니다.
