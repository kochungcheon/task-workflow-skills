# 근거를 읽고 설계와 구현을 검토하기

`design`은 중요한 설계의 빈틈을, `code`는 현재 변경 코드의 결함과 문서 차이를 검토한다. 입력은 원문 요구·고객 답변·`plan.md`·현재 작업 MD·지도·관련 코드와 검토 범위다. [공유 계약](../contracts/task-workflow-v1.md)의 `QualityReview`와 `ToolResult`를 읽는다. 호출자는 검토 결과를 계획·구현·상태에 적용한다.

## 범위와 버전을 고정하기

1. 현재 작업의 요구·인수 기준·결정·고객 질문 ID, `plan_revision / task_revision / map_revision / code_ref`를 읽고 `reviewed_refs`와 `review_scope`에 연결한다. 리뷰 대상과 참조 자료의 경로·버전 또는 내용 해시를 기록한다. 현재 작업이 쓰는 개념 정의·규칙·출처의 정본도 읽기 목록과 `reviewed_refs`에 포함한다. 현재 작업과 후속 작업의 계획을 구분한다.
2. `code`에서는 비교 기준과 대상의 내용을 재식별한다. 구현 착수 때 저장한 기준 커밋과 기존 staged·unstaged·untracked 파일의 본문 또는 패치·내용 해시를 사용하고 `review_scope.change_basis: diff`로 기록한다. 현재 변경에서 기존 사용자 변경을 구분한다.
3. staged·unstaged·untracked 파일과 삭제·이름 변경을 함께 확인한다. 재개·비Git 작업에서 비교 기준을 복원할 수 없으면 `change_basis: current_files`로 관련 파일 전체와 주변 호출자를 검토한다. 이 과제가 만든 변경의 범위는 미확인으로 표시한다. 필수 대상·참조 파일 자체를 읽을 수 없으면 `not_run`으로 반환한다.

커밋 SHA만으로 작업 트리 변경을 대표하지 않는다. `diff`와 `current_files` 모두 현재 파일 목록·내용 해시를 기록하고 실제 읽은 범위에 맞춰 결과를 설명한다.

## 수행자와 근거를 확인하기

수행자 선택·지적 처리·보고서 작성은 호출자가 맡는다. 리뷰어로 위임받았으면 지정한 모드의 검토 기준을 자료에 직접 적용하고, 읽은 범위와 발견 사항을 호출자에게 반환한다.

4. `design`에서 권한·상태 전이·동시성·데이터 정합성·공개 인터페이스·실패 복구를 바꾸는 선택이 있으면 `independence_required: true`로 둔다. 단순하고 확정된 변경은 호출자의 적용 판단과 이유를 연결해 `not_applicable`로 기록할 수 있다.
5. 독립 리뷰는 새 에이전트에 `fork_turns: "none"` 또는 도구가 제공하는 `fork_context: false`를 명시해 실행한다. 모드·검토 범위·이 스킬·지정한 근거 자료만 전달한다. 부모의 대화·내부 추론·예상 정답을 전달하지 않는다. 공유 파일과 프로젝트 지침까지 격리됐다는 주장은 실제 확인한 범위로 제한한다.
6. `code`도 가능하면 구현자와 다른 새 에이전트를 사용한다. 도구가 지원하지 않으면 `reviewer_mode: self`와 이유를 남기고 현재 에이전트가 같은 기준으로 검토한다. 필수 독립 리뷰를 실행할 수 없으면 `not_run`과 필요한 실행 수단을 반환한다.
7. 리뷰어는 지정한 자료와 관련 호출자를 읽고 발견 사항만 반환한다. 파일·코드·작업 상태 변경은 호출자가 맡는다. 실제 수행자 ID, 읽은 자료와 읽기 실패, 완료 결과를 확인한다. 실행 실패·시간 초과·필수 자료 누락은 `not_run`이며 발견 사항 0건과 구분한다.

## design · 구현 전에 검토하기

8. 리뷰어가 먼저 현재 기능의 목표·정책·입력부터 결과까지의 계획을 짧게 재구성하게 한다. 원문·고객 답변·설계 문서 사이의 모순이나 문서만으로 설명할 수 없는 구간을 찾는다. [개념·규칙·출처 기본 점검](../contracts/task-workflow-v1.md#개념과-규칙의-출처-연결)에 따라 주요 용어의 대상·역할·관계와 규칙의 조건·예외·범위를 인수 기준에 대조한다. 이미 명확한 기록은 그대로 재사용한다.
9. 현재 기능의 정상·실패·경계 조건과 검증 가능한 기대값을 확인한다. 권한과 데이터 소유권, 중복·동시 요청, 상태 변경, 외부 실패와 재시도 중 해당 기능의 실제 경계만 검토한다. 중요한 결정과 관련 요구·근거가 연결됐는지 대조한다.
10. 작업 분해·공개 인터페이스·의존관계가 구현과 검증에 충분한지 확인한다. 후속 작업에 필요한 공통 구조도 대조하되, 예정 기능과 현재 구현의 책임을 구분한다. 영향이 작은 내부 선택은 구현자가 판단할 수 있다.

정책 공백은 관련 질문·요구 ID와 함께 [task-customer-interview](../task-customer-interview/SKILL.md), 기술 결정 공백은 [task-design-dialogue](../task-design-dialogue/SKILL.md)로 보낼 내용을 호출자에게 반환한다. 기존 문서에 연결된 실제 답변과 합의를 재사용한다.

## code · 인계 전에 검토하기

11. 변경 파일 전체와 영향을 받는 호출자·저장 구조·검증을 읽는다. 정상 동작, 경계값·오류, 권한·데이터 정합성, 동시 실행·부분 실패·재시도 중 변경이 영향을 주는 경로를 추적한다. 재현 조건과 관찰 가능한 영향을 설명할 수 있는 결함을 우선한다.
12. 원문 요구·고객 답변·인수 기준과 연결된 개념·규칙의 의미를 구현과 대조한다. 같은 용어의 해석이나 적용 범위가 코드 경로마다 달라져 결과가 바뀌는지 확인한다. 테스트의 기대값이 그 근거에서 나왔는지 확인하고, 누락된 회귀 경로를 찾는다. lint·타입·빌드 등 자동 검사 결과는 수행 명령과 현재 코드 버전을 확인한다. 실행 자체는 구현 수행자와 호출자가 맡고, 결과가 없으면 필요한 검사로 반환한다.
13. 계획·지도·실제 코드의 차이를 확인한다. 현재 작업의 누락 기능·잘못된 정책·하드코딩·공개 인터페이스 변경에 실제 코드 위치를 연결한다. 합의된 변경이면 문서 갱신 위치를, 결함이면 수정·재검증할 범위를 반환한다. 코드 스타일은 저장소의 명시적 기준과 유지보수에 미치는 구체적인 영향을 근거로 판단한다.

## 지적 사항을 처리하고 재검토하기

14. 각 지적에 안정적인 ID, `blocker | major | minor`, 위치, 요구 또는 코드 근거, 발생 조건, 영향, 처리 상태와 이유를 기록한다. 호출자는 실제 자료와 대조해 `open | fixed | dismissed | accepted_risk`로 처리한다. 근거 부족한 추정은 확인할 사항으로 남긴다.
15. 수정한 지적은 영향을 받는 코드·문서·테스트를 다시 읽고 `recheck` 근거를 확보한 뒤 해결로 기록한다. `dismissed`에는 적용되지 않는 조건이나 반증을 연결한다. `accepted_risk`에는 판단 주체·선택 이유·영향을 남긴다. 필수 인수 기준 위반이나 실제 `blocker`·`major` 결함은 수정 또는 근거 있는 반증이 필요하다.
16. 기본은 1회 검토 후 주요 수정 범위의 재검토다. 현재 코드·기준이 달라지면 영향받는 리뷰와 검사를 다시 수행한다. 수정 전 통과 근거는 해당 버전의 이력으로 보존한다. 남은 주요 지적이나 미실행 범위는 횟수·시간 한도에 도달해도 결과에 남긴다.

## 결과를 반환하기

`evidence/<task_id>/design-review-<시도>.md` 또는 `code-review-<시도>.md`에 `QualityReview`를 남긴다. 단독 요청은 지정한 출력 위치를 사용하고 작업 ID가 없으면 미정으로 표시한다. 리뷰만 요청받았으면 발견 사항·처리 제안·재검토 조건을 반환한다.

- `pass` — 필요한 범위를 현재 버전에서 검토했고, 필수 독립성 조건을 충족했으며 해결되지 않은 필수 기준 위반과 `blocker`·`major` 결함이 없음.
- `needs_work` — 검토 결과 현재 작업에 수정·정책 확인·설계 결정이 필요한 주요 문제가 남음.
- `not_run` — 필요한 리뷰 수행·자료 확인·비교 범위 확보가 완료되지 않음. 부족한 범위와 재개 조건을 함께 반환.
- `not_applicable` — 해당 모드의 대상이 없는 이유와 확인한 범위가 기록됨. 코드 변경이 있으면 `code` 리뷰가 적용됨.

보고서를 기록했으면 `ToolResult.status: ok`로 반환하고 실제 `verdict`를 함께 둔다. 기록 저장이 실패하면 `status: blocked`와 원인을 반환한다. `task-evidence`는 이 결과와 자동 검사·E2E의 현재 버전을 대조하고, `task-delivery`가 인계·상태 전이를 결정한다.

이 절차는 EGM의 새 컨텍스트 리뷰와 문서·코드 대조 원칙을 현재 작업 MD와 한국어 협업에 맞춰 작성했다. 참고한 원본은 [EGM 리뷰](https://github.com/google/elephant-goldfish-model/blob/5ba5afa03f62627639fa4f71b7ac3bd4d8d07e24/skills/egm-review/SKILL.md), [Codex 컨텍스트 분리](https://github.com/google/elephant-goldfish-model/blob/5ba5afa03f62627639fa4f71b7ac3bd4d8d07e24/docs/codex.md), [문서·코드 대조](https://github.com/google/elephant-goldfish-model/blob/5ba5afa03f62627639fa4f71b7ac3bd4d8d07e24/skills/egm-drift-report/SKILL.md)다.
