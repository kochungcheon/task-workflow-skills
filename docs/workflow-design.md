# 과제 워크플로우

## 무엇을 하는가

과제 MD를 작은 기능으로 나누고, 고객 정책을 확인한 뒤 중요한 기술 선택을 사용자와 논의합니다. 독립적인 요구·코드·환경 조사는 한 계획 초안에 합칩니다. 현재 기능 하나를 TDD로 구현하는 동안 사용자는 HTML 지도와 누적 복습 문서를 읽습니다. 중요한 설계를 독립 리뷰하고, 구현 후 코드 리뷰·자동 검사와 실제 코드·지도 대조를 마쳐 함께 E2E를 확인합니다. 해커톤 모드에서는 사용자가 동작과 선택 이유를 짧게 설명한 뒤 다음 기능으로 갑니다. [전체 워크플로우 그림](workflow.html)

산출물은 `.workflow/<과제명>/` 아래에 둡니다. `plan.md`는 작업 순서·결정·가정·고객 질문과 답변의 원본, `review.md`는 지금까지의 동작·선택·검증·설명 상태를 읽는 요약, `tasks/T01.md`는 현재 기능·검증 기준, `maps/view.html`은 전체 흐름과 작업별 예정/실제 구현·검증 상태, `evidence/T01/`은 실행 근거를 담습니다. 고객 질문 ID에는 답변 주체·출처, 실제 답변과 해석, 관련 요구·작업·인수 기준을 연결합니다. 문서 갱신은 에이전트가 맡습니다.

## 포함한 스킬

| 레이어 | 스킬 | 쓰는 때 |
|---|---|---|
| 자동화 | [task-delivery](../skills/task-delivery/SKILL.md) | 과제 시작부터 분해·구현·공동 검증·다음 기능 진행까지 관리 |
| 도구 | [task-customer-interview](../skills/task-customer-interview/SKILL.md) | 고객 정책·예외를 질문하고 답변을 요구·인수 기준에 연결 |
| 도구 | [task-design-dialogue](../skills/task-design-dialogue/SKILL.md) | 티켓 분해 때와 구현 중 중요한 기술 선택을 사용자와 문답 |
| 도구 | [task-quality-review](../skills/task-quality-review/SKILL.md) | 중요한 설계의 독립 검토와 변경 코드·문서 정합성 리뷰 |
| 도구 | [task-maps](../skills/task-maps/SKILL.md) | 현재 기능의 객체·흐름 지도와 HTML을 만들거나 갱신 |
| 도구 | [task-evidence](../skills/task-evidence/SKILL.md) | 구현 인계·공동 E2E·기능별 사용자 설명의 근거 정리 |
| 도구 | [task-review](../skills/task-review/SKILL.md) | 누적 복습 문서와 기술 인터뷰 연습 질문 정리 |

함께 설치하는 공개 스킬은 `to-tickets`(기능 분해), `tdd`(테스트 후 구현), `codebase-design`(책임·경계), `mermaid-diagrams`(지도 원본), `visual-explainer`(HTML), `simple-english`(영어 기술 문장)입니다. 한국어 문서에는 행위자·조건·결과를 분명히 쓰는 원칙을 적용합니다. `task-delivery`가 필요한 시점에 조합하며 도구의 입출력과 상태는 [공유 계약](../skills/contracts/task-workflow-v1.md)을 따릅니다.

## 개념·규칙·출처의 기본 확인

새 작업·재개하는 현재 작업의 분석과 리뷰에서 구현을 바꾸는 용어·역할·관계, 규칙의 조건·예외와 출처를 항상 확인합니다. 중요한 모호함·해석이 갈리는 공통 규칙·출처 충돌만 기존 `plan.md`의 Q/R/AC 기록에 연결합니다. 업무 범위에 맞는 기존 용어집이나 도메인 정의가 있으면 우선 읽고, 기준은 정본 한 곳에 두며 작업·지도·리뷰에서는 참조합니다. 정본이 없으면 관련 요구·고객 질문에 한두 문장으로 적습니다. 작고 명확한 과제는 기존 기록과 링크를 재사용합니다.

실제 고객 답변, 코드에서 관찰한 사실, AI 가정을 구분합니다. 확인되지 않은 업무 정책은 기존 고객 인터뷰 경로로 보냅니다. 구현·리뷰를 위임할 때 관련 정의·규칙·출처 참조를 함께 전달합니다. 이 확인은 기존 분석·설계·리뷰 단계에서 수행합니다. [기본 점검 계약](../skills/contracts/task-workflow-v1.md#개념과-규칙의-출처-연결)

## 고객 질문이 구현 기준으로 이어지는 경로

`task-delivery`는 초기 분석, 현재 작업의 `ready` 판정 전, 구현·E2E 중 새 정책 의문이나 충돌에서 인터뷰 필요성을 판단합니다. 기본 경로는 에이전트가 질문과 배경을 만들고 사용자가 고객사 담당자·챗봇에 전달해 실제 답변을 가져오는 방식입니다.

`Q01 질문·답변·출처 → R01 요구 → T01 작업·AC 인수 기준 → 구현·검증 근거`로 연결합니다. 실제 답변과 에이전트 해석은 나누어 기록합니다. 고객 확인은 `task-customer-interview`, 기술 선택은 `task-design-dialogue`, 구현 뒤 자기 설명과 복습은 `task-evidence`·`task-review`가 맡습니다.

답변 대기는 질문별로 기록합니다. 현재 작업의 필수 동작을 결정할 수 없으면 해당 작업의 차단 원인과 재개 단계를 남깁니다. 정정 답변으로 기대 결과가 달라지면 이전 답변·검증 이력을 보존하고 계획·작업 버전과 지도를 맞춘 뒤 영향을 받는 검사를 다시 수행합니다. [고객 확인 계약](../skills/contracts/task-workflow-v1.md#customerinterviewnote--고객-정책-확인의-선택-확장)

## 독립 리뷰가 구현과 검증에 연결되는 경로

`task-delivery`는 현재 작업의 권한·상태·동시성·데이터·공개 인터페이스·실패 복구를 바꾸는 중요한 설계에 `task-quality-review`의 `design` 모드를 호출한다. 이전 대화를 전달받지 않은 리뷰어가 원문 요구·고객 답변·계획·작업 MD·지도·관련 코드로 빠진 가정과 실패 경로를 확인한다. 관련 정의·규칙·출처를 읽고 같은 용어·주체·조건이 자료마다 일치하는지도 대조한다. 정책 공백은 고객 인터뷰, 기술 선택의 공백은 설계 대화로 연결한다. 작은 변경의 설계 리뷰 적용 여부와 이유도 기록한다.

TDD 뒤에는 `code` 모드로 기준 시점부터의 실제 변경과 주변 호출 경로를 검토한다. 정의·규칙의 조건·예외가 실제 코드와 검증에 반영됐는지 출처와 대조한다. staged·unstaged·untracked 파일과 기존 사용자 변경의 경계를 포함한다. 프로젝트의 lint·타입·빌드·관련 테스트를 확인하고 주요 지적을 수정한 뒤 영향받는 검사와 리뷰를 다시 확인한다. 현재 코드의 필수 리뷰·검사 근거가 준비되면 지도·인계·공동 E2E로 이어간다.

Python 작업에서는 [Python 코드 가이드](../skills/contracts/python-guidelines.md)를 분석·설계부터 읽고 프로젝트의 적용 규약·환경·검사 명령을 정한다. 도메인·계층·트랜잭션 기준을 구현자와 리뷰어에게 함께 전달하고, Ruff 등 실제 검사 결과를 같은 과제의 ImplementationChecks에 연결한다. 설치된 스킬 묶음의 상대 경로로 가이드에 접근할 수 있다.

리뷰 결과에는 검토 범위·대상 버전·수행자·지적 사항·처리 근거를 연결한다. 독립 실행 지원 여부와 실제 완료를 확인하고 미실행은 `not_run`으로 남긴다. 해커톤에서는 중요한 설계의 1회 검토와 주요 수정의 재검토부터 수행한다. `task-review`는 이 결과를 누적 복습 문서에 연결한다. [리뷰 도구](../skills/task-quality-review/SKILL.md)

## 어떻게 쓰는가

[상황별 호출 문장과 생성 파일](usage-examples.md)을 한 문서에서 볼 수 있습니다.

1. [README](../README.md)의 명령으로 패키지를 설치하고 과제 MD 경로를 줍니다. “이 과제를 3시간 해커톤 워크플로우로 진행하자. 티켓과 중요한 기술 선택의 초안을 먼저 보여줘”라고 요청하거나 `$task-delivery <과제 MD 경로>`로 시작합니다.
2. 에이전트가 독립적인 사실 조사를 병렬로 수행할 수 있습니다. 결과를 계획 초안에 합치고 필요한 고객 질문을 정리합니다. 사용자가 가져온 답변으로 요구·인수 기준을 구체화한 뒤 중요한 기술 선택에 답하거나 반론을 제기합니다. 질문·답변·결정·남은 가정은 `plan.md`와 지도에 연결합니다. 독립성이 애매한 조사는 순차로 진행합니다.
3. 현재 작업 MD와 지도를 확인하고 중요한 설계의 독립 리뷰 결과를 반영합니다. TDD 전에 HTML의 현재 작업 기록에서 예정 코드 경로·선택 이유·검증 지점을 읽습니다. `review.md`에는 지금까지의 완료 기능과 기술 선택을 누적합니다. 사용자는 구현 중 두 문서를 읽고, 에이전트는 같은 작업의 E2E를 준비합니다. 구조·결정이 바뀌면 구현을 멈추고 지도 갱신을 알립니다. 구현 후 코드 리뷰·자동 검사·영향 재검증을 마치고 인계 때 계획과 실제 코드·E2E 절차를 연결합니다.
4. 함께 실제 입력부터 결과까지 E2E를 확인합니다. 실패하면 같은 작업을 수정합니다. 통과하면 사용자가 동작·선택 이유·한계를 자기 말로 짧게 설명하고 `review.md`의 설명 상태·다음 대화 지점을 갱신한 뒤 다음 작업으로 갑니다.

독립 설계·코드 리뷰는 `task-quality-review`, 고객 정책 확인만 필요하면 `task-customer-interview`, 설계 대화만 필요하면 `task-design-dialogue`, 지도만 필요하면 `task-maps`, 완료 근거만 필요하면 `task-evidence`, 누적 복습만 필요하면 `task-review`를 직접 요청합니다. 최종 문서에는 실제 선택에서 나온 기술 인터뷰 연습 질문을 모읍니다. 사용자가 답하면 원문·근거를 대조해 갱신합니다.
