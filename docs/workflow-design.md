# 공유 지도와 공동 검증을 중심으로 한 설계

## 원하는 협업

과제를 작은 완결 기능으로 나누고 사용자와 에이전트가 같은 객체 지도·프로젝트 흐름 지도를 봅니다. 에이전트는 현재 기능의 TDD를 수행하고 코드·지도·검증 근거를 인계합니다. 사용자와 실제 경로를 확인한 뒤 다음 기능으로 진행합니다.

사용자는 전체 구조와 현재 위치를 기억하고, 에이전트는 새 컨텍스트에서도 같은 과제와 지도에서 이어받습니다. 전체 작업의 구현 결과뿐 아니라 사용자의 지시·판단·설명 근거도 남길 수 있는 구조입니다.

## 두 레이어

`task-delivery`는 현재 작업과 순서·분기·대기·재개를 관리합니다. 도구 스킬은 입력을 받아 산출물·판정·부족한 근거를 반환합니다.

`task-maps`는 책임 설계가 필요한 경우 `codebase-design`을 참고합니다. `mermaid-diagrams`로 원본을, `visual-explainer`로 사람이 읽을 HTML을 작성합니다. 같은 노드 ID·지도 버전·실제 코드 위치를 유지합니다.

`task-evidence`의 handoff는 구현 결과를 인계하고 joint-e2e는 실제 실행 관찰을 기록합니다. 실행 성공과 기능 통과를 구분합니다. 도구가 실패 보고서를 정상 생성해도 과제가 통과한 것은 아닙니다.

## 현재 기능 하나를 완주하는 이유

각 과제는 입력부터 관찰 가능한 결과까지 연결합니다. 객체와 처리 경로를 먼저 공유해 구현 의도를 확인하고, 합의한 공개 경계에서 실제 테스트 실패와 통과를 기록합니다. 전체 테스트를 먼저 작성한 뒤 전체 구현을 한꺼번에 수행하는 방식은 기본 절차가 아닙니다.

에이전트의 구현 보고 뒤에는 `awaiting_joint_e2e`가 있습니다. 현재 코드·기준의 필수 경로 통과와 사용자 결과 확인 후에만 `verified`가 됩니다. 실패하면 현재 과제의 재현·수정·재검증으로 돌아갑니다. 상태의 정확한 계약은 [공유 계약](../skills/contracts/task-workflow-v1.md)에 있습니다.

## 다른 환경으로 이동하는 방법

개인 컴퓨터 경로를 제거하고 파일 위치 기준의 상대 참조를 사용합니다. 3개 스킬, 공통 계약, 5개 공개 스킬과 참조 자원을 같은 상위 폴더에 설치합니다. 단일 SKILL.md만 설치하는 방식은 이 묶음의 공유 계약을 보존하지 못합니다.

공개 원문은 커밋과 파일 해시로 고정합니다. 출처 URL은 원본 확인과 명시적인 업데이트에 사용합니다. 설치된 파일이 없으면 환경의 스킬 목록에서 같은 이름을 찾고 버전 차이를 확인합니다. [구성 요소와 경로 해석](../skills/contracts/components.md).

## 도구 변경의 영향

같은 계약에서 내부 구현만 바꾸면 도구 기능과 영향을 받는 회귀를 확인합니다. 입력·출력·실패 의미가 바뀌면 계약 버전과 호출자의 해석도 맞춥니다. 정상 인계, E2E 실패 복귀, 사용자 확인 누락, 오래된 지도, 필수 출력 누락이 검토 대상입니다.

## 확인한 범위와 남은 검증

스킬 형식·참조·이식 설치·공개 원문 해시와 HTML 표현을 점검합니다. 이 검사는 실제 과제 한 회차의 성공이나 사용자 이해도를 증명하지 않습니다. 첫 실제 작업에 적용해 과제 크기·지도 관리 비용·인계 정보의 충분성을 확인해야 합니다.

전체 작업 후 자기 설명을 6문항으로 연습하는 것은 별도 훈련 설계입니다. 현재 task-delivery의 자동 후속 호출과 전용 프롬프트 자동 채점은 포함하지 않습니다.
