# 공유 지도와 공동 검증을 중심으로 한 설계

## 원하는 협업

과제 MD를 읽고 티켓을 나눌 때 중요한 기술적 갈림길을 함께 찾습니다. 선택지·추천·이유와 관련 작업을 초안으로 보여주고, 현재 작업에 필요한 판단부터 대화합니다. 전체 구현 방향·결정 이유는 plan.md, 현재 기능의 구체적인 범위·검증은 작업 MD에 둡니다. 사용자와 에이전트는 같은 객체·프로젝트 흐름 지도를 읽습니다. 에이전트가 TDD를 수행하고 근거를 인계하면 공동 E2E로 실제 경로를 확인합니다. 해커톤·시험 대비에서는 짧은 자기 설명과 복습 기록을 남긴 뒤 다음 기능으로 진행합니다.

초안은 과제 원문·기존 코드에서 확인할 사실과 여러 타당한 선택 중 사용자 판단이 필요한 결정을 구분합니다. 중요한 기술 선택은 초안을 보고 함께 고치며, 아직 확인하지 않은 가정은 영향·확인 시점·적용 위치와 함께 남깁니다. 사용자가 판단을 위임하면 에이전트 선택으로 표시합니다. 이 순서는 [GPTaku show-me-the-prd](https://github.com/fivetaku/show-me-the-prd)의 초안 우선 원칙을 참고해 이미 요구 MD가 있는 3시간 과제에 맞춘 것입니다. 4종 제품 기획 문서나 고정 질문 횟수를 그대로 가져오지 않습니다.

[oh-my-ouroboros](https://github.com/DaeSeokSong/oh-my-ouroboros)는 전역 Claude Code 하네스로, intent 커밋·단계별 평가표와 승인·다중 에이전트·월간 감사를 포함합니다. 그 `/discuss`는 여러 에이전트의 내부 토론이므로, 사용자와 AI가 설계를 주고받는 우리 핵심 대화를 대신하지 않습니다. 구현량이 많은 3시간 과제에는 전체 절차보다 기존 구조에서 이어받는 전제, 선택지별 실제 예, 검증 출력에 근거한 완료 판단만 현재 문서와 인계에 반영합니다. 별도 intent/PRD 문서를 필수로 만들지 않습니다. 초기에 설계를 충분히 논의한 결과를 한 계획과 지도에 압축합니다.

사용자는 전체 구조와 현재 위치를 기억하고, 에이전트는 새 컨텍스트에서도 같은 과제와 지도에서 이어받습니다. 전체 작업의 구현 결과뿐 아니라 사용자의 지시·판단·설명 근거도 남길 수 있는 구조입니다.

## 두 레이어

`task-delivery`는 현재 작업과 순서·분기·대기·재개를 관리합니다. `task-design-dialogue`는 초안의 중요한 기술 선택을 사용자와 문답하며 결정·가정을 `plan.md`에 남기고, 작업·지도·검증에 달라질 지점을 호출자에게 돌려줍니다. 사용자의 질문과 반론으로 초안을 고치며, 설계가 설명 가능해지면 현재 기능부터 구현합니다. 도구 스킬은 입력을 받아 산출물·판정·부족한 근거를 반환합니다.

`task-maps`는 책임 설계가 필요한 경우 `codebase-design`을 참고합니다. `mermaid-diagrams`로 원본을, `visual-explainer`로 사람이 읽을 HTML을 작성합니다. 같은 노드 ID·지도 버전·실제 코드 위치를 유지합니다.

`task-evidence`의 handoff는 구현 결과를 인계하고 joint-e2e는 실제 실행 관찰을 기록합니다. learning-review는 현재 코드와 사용자의 실제 설명을 대조해 이해 기록을 만듭니다. 실행 성공·기능 통과·사용자 이해는 각각 근거를 확인합니다. 도구가 실패 보고서를 정상 생성해도 과제가 통과한 것은 아닙니다.

## 3시간과 읽을 화면

초기 요구 파악·결정·분해·첫 지도 15분, 기능 반복 145분, 최종 실행·제출·복습 정리 20분을 조정 가능한 기본안으로 둡니다. 환경·문서 작성·화면 확인도 포함합니다. 실제 한 기능의 시간을 확인해 분량과 작업 크기를 조정해야 합니다.

사용자는 maps/view.html 한 화면에서 전체 위치와 현재 기능의 요구 연결·동작 경로·선택 이유·실패 조건·검증 근거를 봅니다. 중요한 결정 모두의 ID·상태·선택 이유·대안 조건을 관련 객체 노드와 함께 찾을 수 있고, 현재 기능의 결정은 첫 화면에 표시합니다. 문서 갱신은 에이전트가 맡습니다. 공통 결정은 plan.md가 원본이고 작업 MD가 ID로 참조합니다. 전체 순서를 먼저 정하고 현재 기능부터 상세화합니다. 결정 설명만 바뀌면 구조 지도 버전을 올리지 않고 HTML 요약과 계획 버전을 맞출 수 있습니다.

공동 E2E 뒤 60~90초 자기 설명을 확인합니다. `verified`는 기능 검증이며, `learning_status`의 `explained / revisit / deferred / pending`과 분리합니다. 막힌 부분은 짧게 보충하고 복습 기록을 남겨 진행할 수 있습니다. 미응답은 기다리고 명시적인 설명 보류는 기록합니다. 일반 개발에서는 이 학습 모드를 생략합니다. [해커톤 절차](../skills/task-delivery/references/hackathon.md).

## 현재 기능 하나를 완주하는 이유

각 과제는 입력부터 관찰 가능한 결과까지 연결합니다. 객체와 처리 경로를 먼저 공유해 구현 의도를 확인하고, 합의한 공개 경계에서 실제 테스트 실패와 통과를 기록합니다. 전체 테스트를 먼저 작성한 뒤 전체 구현을 한꺼번에 수행하는 방식은 기본 절차가 아닙니다.

에이전트의 구현 보고 뒤에는 `awaiting_joint_e2e`가 있습니다. 현재 코드·기준의 필수 경로 통과와 사용자 결과 확인 후에만 `verified`가 됩니다. 실패하면 현재 과제의 재현·수정·재검증으로 돌아갑니다. 상태의 정확한 계약은 [공유 계약](../skills/contracts/task-workflow-v1.md)에 있습니다.

## 다른 환경으로 이동하는 방법

개인 컴퓨터 경로를 제거하고 파일 위치 기준의 상대 참조를 사용합니다. 작성한 4개 스킬, 공통 계약, 5개 공개 스킬과 참조 자원을 같은 상위 폴더에 설치합니다. 단일 SKILL.md만 설치하는 방식은 이 묶음의 공유 계약을 보존하지 못합니다.

공개 원문은 커밋과 파일 해시로 고정합니다. 출처 URL은 원본 확인과 명시적인 업데이트에 사용합니다. 설치된 파일이 없으면 환경의 스킬 목록에서 같은 이름을 찾고 버전 차이를 확인합니다. [구성 요소와 경로 해석](../skills/contracts/components.md).

## 도구 변경의 영향

같은 계약에서 내부 구현만 바꾸면 도구 기능과 영향을 받는 회귀를 확인합니다. 입력·출력·실패 의미가 바뀌면 계약 버전과 호출자의 해석도 맞춥니다. 정상 인계, E2E 실패 복귀, 사용자 확인 누락, 오래된 지도, 필수 출력 누락이 검토 대상입니다.

## 확인한 범위와 남은 검증

스킬 형식·참조·이식 설치·공개 원문 해시와 HTML 표현을 점검합니다. ROOM-TS-1 시범 과제에서 기능 검증은 완료됐으나 180분 적합성과 사용자 설명 효과는 측정되지 않았습니다. 티켓 분해 시 결정 대화와 지도 표시의 새 흐름은 다음 실습에서 확인해야 합니다.

기능별 자기 설명은 task-delivery에서 연결합니다. 전체 작업 후 6문항 연습은 별도 요청으로 다루며, 이 패키지는 해당 문항 자동 출제나 프롬프트 자동 채점을 포함하지 않습니다.
