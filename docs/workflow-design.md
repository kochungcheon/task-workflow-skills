# 과제 워크플로우

## 무엇을 하는가

과제 MD를 작은 기능으로 나누고, 구현 방향을 바꾸는 기술적 선택은 사용자와 먼저 논의합니다. 에이전트가 한 기능씩 TDD로 구현하면 사용자는 객체·흐름 HTML 지도와 작업 문서로 맥락을 읽습니다. 구현 후 함께 E2E를 확인하고, 사용자가 동작과 선택 이유를 짧게 설명한 뒤 다음 기능으로 갑니다.

산출물은 `.workflow/<과제명>/` 아래에 둡니다. `plan.md`는 작업 순서·결정·가정, `tasks/T01.md`는 현재 기능·검증 기준, `maps/view.html`은 객체 책임·실행 경로·현재 위치, `evidence/T01/`은 구현·검증 근거를 담습니다. 문서 갱신은 에이전트가 맡습니다.

## 포함한 스킬

| 레이어 | 스킬 | 쓰는 때 |
|---|---|---|
| 자동화 | [task-delivery](../skills/task-delivery/SKILL.md) | 과제 시작부터 분해·구현·공동 검증·다음 기능 진행까지 관리 |
| 도구 | [task-design-dialogue](../skills/task-design-dialogue/SKILL.md) | 티켓 분해 때와 구현 중 중요한 기술 선택을 사용자와 문답 |
| 도구 | [task-maps](../skills/task-maps/SKILL.md) | 현재 기능의 객체·흐름 지도와 HTML을 만들거나 갱신 |
| 도구 | [task-evidence](../skills/task-evidence/SKILL.md) | 구현 인계·공동 E2E·사용자 설명의 근거 정리 |

공개 스킬 `to-tickets`·`tdd`·`codebase-design`·`mermaid-diagrams`·`visual-explainer`도 함께 설치합니다. 분해·테스트·책임 설계·지도 원본·HTML 작성에 각각 사용합니다. `task-delivery`가 필요한 시점에 조합합니다.

## 어떻게 쓰는가

1. [README](../README.md)의 명령으로 패키지를 설치하고 과제 MD 경로를 줍니다. “이 과제를 3시간 해커톤 워크플로우로 진행하자. 티켓과 중요한 기술 선택의 초안을 먼저 보여줘”라고 요청하거나 `$task-delivery <과제 MD 경로>`로 시작합니다.
2. 에이전트가 요구·코드를 읽고 작업 순서와 선택지·추천을 제시하면, 사용자는 중요한 선택에 답하거나 반론을 제기합니다. 결정과 남은 가정은 `plan.md`와 지도에 반영됩니다.
3. 현재 작업 MD와 지도를 확인합니다. 에이전트는 TDD로 구현하고 실제 테스트 결과와 E2E 절차를 인계합니다. 사용자는 `maps/view.html`에서 결정 이유와 코드 흐름을 읽습니다.
4. 함께 실제 입력부터 결과까지 E2E를 확인합니다. 실패하면 같은 작업을 수정합니다. 통과하면 사용자가 동작·선택 이유·한계를 자기 말로 짧게 설명하고 다음 작업으로 갑니다.

설계 대화만 필요하면 `task-design-dialogue`, 지도만 필요하면 `task-maps`, 완료 근거만 필요하면 `task-evidence`를 직접 요청합니다. 작업 후 6문항 연습은 별도로 요청할 때 진행합니다.
