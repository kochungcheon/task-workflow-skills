# 워크플로우 사용 예제

아래 문장은 **과제 프로젝트에서 Codex에게 보내는 메시지**입니다. 터미널 명령이 아닙니다. `./requirements.md`는 실제 과제 MD 경로로, `.workflow/<과제명>/`은 해당 과제의 작업 폴더로 바꿔 쓰세요. 설치 방법은 [README](../README.md#어떻게-쓰는가)에 있습니다.

## 무엇을 직접 호출하나

| 상황 | 호출 | 에이전트가 이어서 하는 일 |
|---|---|---|
| 과제 시작·구현·중단 후 재개 | [`task-delivery`](../skills/task-delivery/SKILL.md) | 요구 분석·필요한 고객 인터뷰 → 분해·기술 선택 문답 → 지도 → 중요한 설계 독립 리뷰 → 현재 티켓 TDD → 코드 리뷰·자동 검사 → 인계 → 공동 E2E → 다음 티켓. 해커톤에서는 누적 복습도 갱신 |
| 고객 정책·업무 예외 확인 또는 답변 반영 | [`task-customer-interview`](../skills/task-customer-interview/SKILL.md) | 필요한 질문과 배경을 작성하고 실제 답변·출처를 요구·인수 기준에 연결 |
| 중요한 설계 선택만 논의 | [`task-design-dialogue`](../skills/task-design-dialogue/SKILL.md) | 근거·선택지·절충을 문답하고 `plan.md` 결정에 반영 |
| 중요한 설계 또는 변경 코드 검토 | [`task-quality-review`](../skills/task-quality-review/SKILL.md) | design/code 모드의 검토 범위·버전·지적·처리 근거 기록 |
| 지도만 만들거나 최신 코드에 맞춤 | [`task-maps`](../skills/task-maps/SKILL.md) | 객체·흐름 원본과 `maps/view.html` 갱신 |
| 현재 기능의 인계·공동 검증·설명 기록만 정리 | [`task-evidence`](../skills/task-evidence/SKILL.md) | 현재 티켓의 실행·사용자 확인 근거 기록 |
| 지금까지 또는 전체 과제를 복습 | [`task-review`](../skills/task-review/SKILL.md) | `review.md`를 코드·검증 근거와 대조해 갱신하고 기술 질문 준비 |

`$task-delivery`로 시작했다면 하위 스킬은 해당 단계에서 에이전트가 사용합니다. 고객 인터뷰는 초기 분석, 현재 작업의 `ready` 판정 전, 구현·검증 중 새 정책 의문이 생겼을 때 필요에 따라 호출합니다. 특정 결과만 다시 보고 싶을 때 해당 도구 스킬을 직접 요청하세요.

## 1. 새 과제: 3시간 해커톤 모드

```text
$task-delivery ./requirements.md
3시간 해커톤 모드로 시작하자. 원문 요구와 기존 코드를 보고 작은 티켓·의존관계·중요한 기술 선택의 초안을 먼저 보여줘. 선택지의 장단점과 추천 이유를 나와 논의한 뒤 현재 티켓의 작업 MD, 객체·흐름 지도와 review.md를 만들어줘. 중요한 설계를 독립 검토한 뒤 한 티켓씩 TDD로 구현하자. 구현 후 코드 리뷰·자동 검사와 주요 지적의 재검증을 마치고, 인계 뒤에는 나와 공동 E2E를 확인하자.
```

에이전트는 `plan.md`와 현재 `tasks/T01.md`를 만들고, 구현 전 `maps/view.html`에 예정 경로와 선택 이유를 표시합니다. 구현 중에는 사용자가 지도와 `review.md`를 읽습니다. 중요한 선택에 답할 때는 추천을 그대로 받아들이거나 조건을 추가해도 됩니다. 현재 구현을 바꾸는 미결정은 대화에서 해결한 뒤 구현합니다.

### 계획과 지도까지만 먼저 볼 때

```text
$task-delivery ./requirements.md
요구를 작은 티켓으로 나누고 중요한 기술적 갈림길을 나와 논의하자. plan.md와 현재 티켓의 객체·흐름 HTML 지도까지 만든 뒤 보여줘. 구현은 내가 지도를 읽고 이어서 요청할게.
```

### 일반 개발 모드로 시작할 때

```text
$task-delivery ./requirements.md
일반 개발 모드로 진행하자. 중요한 선택과 현재 티켓의 지도를 공유하고, 한 티켓씩 TDD·인계·공동 E2E로 검증해줘.
```

일반 모드는 3시간 시간 배분·기능별 자기 설명을 기본 단계로 추가하지 않습니다. 현재 티켓 하나씩 구현하고 공동 E2E로 확인하는 흐름은 같습니다.

## 2. 진행 중: 한 지점만 다룰 때

### 고객에게 확인할 정책을 찾을 때

```text
$task-customer-interview ./requirements.md .workflow/<과제명>/plan.md
요구사항과 코드를 보고 현재 기능의 동작을 결정하려면 고객에게 확인해야 할 업무 정책·예외를 찾아줘. 내가 고객사 챗봇에 전달할 질문과 질문 이유를 정리하고, 기존 plan.md에 질문 ID와 영향받는 요구·작업을 연결해줘.
```

에이전트가 질문을 작성하면 사용자가 고객사 담당자나 챗봇에 전달합니다. 고객 답변을 가져올 때는 어느 질문에 대한 답인지, 답변 주체와 원문을 함께 제공합니다. 기술 선택은 `task-design-dialogue`, 구현 후 설명 연습은 `task-review`에서 다룹니다.

### 고객 답변을 받아 구현을 재개할 때

```text
$task-delivery ./requirements.md
Q01에 대해 고객사 챗봇의 [담당자 역할]이 “[실제 답변]”이라고 답했어. 적용 범위는 [확인한 조건]이야. 기존 .workflow/<과제명>/plan.md에 답변 출처와 해석을 구분해 기록하고, 관련 요구·작업·인수 기준을 갱신한 뒤 현재 작업을 이어줘.
```

답변이 모호하거나 원문과 충돌하면 같은 질문에 후속 확인을 연결합니다. 답변 대기는 질문별로 기록하고, 현재 작업의 필수 동작을 결정할 수 없는 경우 그 작업의 차단 원인으로 기록합니다. 답변 정정으로 기대 결과가 바뀌면 영향받는 테스트·E2E도 새 기준으로 확인합니다.

### 기술 선택을 더 이야기할 때

```text
$task-design-dialogue ./requirements.md .workflow/<과제명>/plan.md
D02가 현재 티켓의 저장 방식에 영향을 주는지 코드와 요구를 근거로 확인하자. 가능한 선택지, 실패 상황, 대안이 더 나은 조건을 먼저 보여줘. 내 답을 듣고 결정과 남은 가정을 plan.md에 반영해줘.
```

### 중요한 설계를 독립 리뷰할 때

```text
$task-quality-review .workflow/<과제명>/tasks/T01.md
design 모드로 원문 요구·고객 답변·계획·두 지도·관련 코드를 새 리뷰어에게 전달해 검토해줘. 이전 대화 없이 문서에서 확인되는 근거로 숨은 가정·실패 경로·구현 가능성을 살펴보고 주요 지적을 기록해줘.
```

### 구현 뒤 변경 코드를 리뷰할 때

```text
$task-quality-review .workflow/<과제명>/tasks/T01.md
code 모드로 작업에 기록된 기준 시점부터 현재 코드까지 검토해줘. staged·unstaged·untracked 변경과 주변 호출 경로를 포함하고 요구·고객 정책·권한·동시성·회귀 위험을 대조해줘. 지적마다 실제 위치·발생 조건·영향·근거를 남겨줘.
```

리뷰 대상 버전과 범위를 먼저 확인합니다. `task-delivery`에서 진행하면 주요 지적의 수정과 영향받는 검사·리뷰 확인까지 연결합니다. 필수 독립 검토가 실행되지 않았으면 미실행 원인을 남깁니다.

### 지도만 갱신할 때

```text
$task-maps .workflow/<과제명>/tasks/T01.md
plan.md의 결정과 현재 코드를 대조해 객체 지도·흐름 지도·maps/view.html을 갱신해줘. 계획과 실제가 달라진 곳, 아직 구현하지 않은 곳을 구분해줘.
```

HTML이 이미 열려 있으면 갱신 후 새로고침합니다.

### 합의한 티켓을 구현하거나 재개할 때

```text
$task-delivery ./requirements.md
기존 .workflow/<과제명>/와 현재 코드를 대조하고 T01부터 이어줘. 합의한 지도·인수 기준으로 TDD를 진행하고, 실제 Red/Green, 코드 리뷰, 프로젝트 자동 검사와 주요 지적의 재검증을 확인한 뒤 구현 인계와 공동 E2E 절차를 보여줘.
```

구현 인계는 `awaiting_joint_e2e` 상태입니다. 이때 에이전트가 자동 검사 결과와 함께 실제 입력·행동·기대 결과를 보여줍니다.

## 3. 함께 검증하고 다음 티켓으로 갈 때

### 공동 E2E를 실행할 때

```text
$task-delivery ./requirements.md
T01 구현 인계를 읽었어. 제시한 입력으로 실제 진입점부터 결과까지 공동 E2E를 같이 확인하자. 내가 확인해야 할 화면·응답·저장 결과를 차례로 알려줘.
```

실제 결과를 확인한 뒤에는 관찰한 내용을 말해 주세요. 에이전트 실행만으로 사용자 확인을 대신 기록하지 않습니다.

```text
T01 E2E에서 [입력]을 넣었고 [실제 화면·응답·저장 결과]를 확인했어. 이 기능은 [입력→처리→결과]로 흐르고, [핵심 선택]을 한 이유는 [이유]야. 확인한 내용과 설명을 기록하고 다음 티켓으로 가자.
```

결과가 다르면 같은 티켓에서 수정하도록 관찰을 전달합니다.

```text
T01 E2E에서 [입력]을 넣었는데 기대한 [결과] 대신 [실제 결과]가 나왔어. 실행 근거를 남기고 같은 티켓에서 원인을 찾아 수정한 뒤 다시 검증하자.
```

### 인계·검증·기능 설명 기록만 다시 정리할 때

```text
$task-evidence .workflow/<과제명>/tasks/T01.md
handoff 모드로 현재 코드·Red/Green 실행 기록을 대조하고, T01의 구현 인계와 공동 E2E 준비 상태를 정리해줘.
```

```text
$task-evidence .workflow/<과제명>/tasks/T01.md
joint-e2e 모드로 [실제 입력·행동·관찰 결과]와 내가 확인한 [결과]를 기록해줘. 미실행 구간도 구분해줘.
```

```text
$task-evidence .workflow/<과제명>/tasks/T01.md
learning-review 모드로 내 설명 “[입력부터 결과까지의 흐름과 선택 이유]”를 현재 코드와 대조하고, 막힌 부분을 T01의 이해 기록에 남겨줘.
```

## 4. 끝날 때: 전체 리뷰와 인터뷰 연습

`$task-delivery`로 마지막 티켓까지 진행하면 에이전트가 `task-review`를 호출해 `review.md`의 전체 동작 경로, 중요한 선택·절충, 검증 근거, 남은 복습 질문을 다시 대조합니다. 나중에 별도로 복습할 때는 다음처럼 요청합니다.

```text
$task-review .workflow/<과제명>/
과제 전체를 현재 코드와 대조해 review.md를 갱신하고 나와 함께 읽자. 30초 설명부터 전체 흐름, 중요한 기술 선택과 대안, 실패 조건, 검증한 범위를 짚어줘. 실제 결정에서 나온 기술 질문을 하나씩 해주고, 내 답을 근거와 비교해 빈틈을 기록해줘.
```

6문항 연습을 하고 싶다면 “근거가 있는 질문으로 6문항 연습하자”를 덧붙입니다. 질문 수를 채우려고 사소한 구현 세부 사항을 만들지 않습니다. 답하지 않은 질문은 `미응답`으로 남습니다.

제출 전 실행 방법과 요구별 근거까지 점검할 때는 다음처럼 요청합니다.

```text
$task-delivery ./requirements.md
마지막 티켓까지의 검증 상태와 제출 요구별 근거를 현재 코드와 대조해줘. 실행 방법, 남은 미검증 범위, 최종 review.md를 보여줘.
```

## 생성되는 산출물

| 경로 | 읽는 목적 |
|---|---|
| `.workflow/<과제명>/plan.md` | 전체 티켓 순서·기술 결정·고객 질문 ID와 답변 출처·해석·관련 요구/작업/인수 기준 |
| `.workflow/<과제명>/tasks/T01.md` | 현재 기능의 요구·구현·검증·설명 상태 |
| `.workflow/<과제명>/maps/view.html` | 전체 흐름에서 현재 기능의 위치와 객체·실행 경로 |
| `.workflow/<과제명>/evidence/T01/` | 설계·코드 리뷰, 자동 검사, TDD 인계·공동 E2E의 실제 근거 |
| `.workflow/<과제명>/review.md` | 지금까지의 내용과 최종 인터뷰 복습 브리프 |
